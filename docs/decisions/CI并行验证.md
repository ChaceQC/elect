# CI 并行验证第一轮

日期：2026-10-05（Asia/Shanghai）。本轮仅调整验证编排与镜像传递，不改变应用版本、业务行为或生产启动顺序。

## 范围与门禁

第一轮保留所有分支 push、main PR、版本标签的完整验证，并提供手动完整验证入口。不做路径跳过，不切换日常 push 快速检查。第二轮才调整触发分层。

前后端检查与构建分别运行；两端成功后，业务与消息集成、13／30 容器兼容、七容器与交付恢复在三个独立运行器并行。`容器验证 / check` 始终执行汇总，严格要求这五个作业全部 success；失败、取消、缺失和跳过都拒绝。标签发布单独依赖 check，只有发布作业拥有 contents/packages 写权限。分支与 PR 分别取消过时运行，标签单独分组且不取消正在发布的同标签运行。

## 覆盖与状态契约

| 作业 | 现有覆盖 | 前置与结束状态 |
| --- | --- | --- |
| 后端 | Ruff、单元、契约、schema、迁移清单及 SQL、查询受理数据库定向验证 | 构建本次 runtime/test；独立临时 MySQL 与 internal 网络 |

环境准备从 test-stack 抽出，负责校验镜像、一次性 Secret、空库迁移、基础健康及按组启动；不会执行业务用例。普通本地 test-stack 保留一条命令构建、准备并完整验证的入口，CI 使用已加载镜像并禁止重建。每个独立脚本显式检查其前置状态，不依赖其他作业留下数据库内容。

CI 使用含 run ID、attempt 和组名的独立项目名、目录、卷与网络。Secret 在各运行器内生成，不上传；恢复所需 Secret 仅在交付组内部复制到独立恢复目标。清理仅删除本次明确命名项目的容器和卷，不操作其他项目。生产 start/upgrade 仍串行启动；无源码部署和模式切换演练继续调用真实入口。

## 镜像传递与缓存

前后端各输出 runtime 和测试镜像包，以及版本、检出提交、镜像 ID、文件 SHA-256。PR 使用默认检出的合并结果；构建、测试和清单校验都针对该提交。消费方先核对版本、提交和包校验值，再加载并核对镜像 ID/OCI 标签。恢复复用本次 runtime/test，不再构建 ops。

BuildKit GHA 缓存按前后端/目标分开，只缓存构建层；每次重新执行检查和业务验证。标签发布重新校验并只加载受测 runtime，再由现有 publish.sh 发布，不重新构建。Actions artifact 只包含镜像和公开校验信息，不传卷、会话、测试凭据或完整临时目录。

打包、上传、下载、加载分别记录耗时。镜像大小和传输开销以实际 Actions 为准；后续比较冷缓存与命中缓存，不能用理论并行度代替提速证据。

## 验证计划与基线

只增加针对汇总失败处理和镜像一致性拒绝路径的定向检查，使用 actionlint、shell 语法检查与一轮实际完整 PR Actions 验收，不在本机重复全套容器演练。
