# 付款后余额独立读取

日期：2026-10-08（Asia/Shanghai）。版本：0.22.5。仅修复本轮全仓审查问题4，保留问题1—3修复；问题5、6未处理。现有部署本轮不升级。

## 问题与规则

Payment取得学校付款确认后，使用固定订单键请求Room刷新余额。原受理逻辑会合并到该账号已有余额任务；若旧B02已经取得付款前余额、响应或本域提交尚未完成，旧根的成功会传播到支付别名，使页面提前显示“学校余额已重新查询”。观测序号只能防止缓存倒退，无法单独证明支付任务执行过付款后的读取。

支付来源的新请求保留独立read_school根任务，不参与已有根任务合并。即使已有任务仍处于accepted，或来源是另一个订单，也不复用它。新任务只在付款确认后受理，随后由既有Room领取器发起B02；不依赖跨域时钟比较，也无需新增观测下界字段。

## 幂等、并发与恢复

- 受理仍在本人偏好行锁内先检查原键，再校验active绑定和系统6次/分钟、60次/滚动24小时、8个待办预算。支付来源只信任已验证的payment签名身份；浏览器不能通过传source取得系统用途。
- 同订单继续使用payment-paid:order_id固定键，响应丢失、并发重放和进程重启返回原operation，不重复创建新任务。每个新订单独立受理并计额，额度不足沿用原429与重试。
- 原owner串行领取、45秒租约、SKIP LOCKED和学校账号锁保持。已有读取仍有效时，支付任务等待；旧租约失效后的迟到响应不能越过既有提交栅栏。没有新增线程、连接池、学校并发或容器。
- 浏览器请求继续合并可用根任务、遵守30秒冷却；可以等待已受理的支付根任务。支付成功只依赖自己的读取结果，旧根成功或失败都不能替它终结。
- 旧版本尚未终结的request_source=payment合并别名，不再由根任务提交或分批别名传播继承结果。领取器在原owner/任务锁内解除合并，沿用原operation和订单关联独立执行B02；根仍运行或已完成均可恢复。
- 已有succeeded/failed/cancelled终态不重新查询、不改写，归档键与历史记录保持。升级按既有停旧角色流程进行，禁止混跑仍会传播支付别名终态的旧Room进程；无需新迁移、批量维护命令或生产数据改写。

## 状态与范围

付款事实保持paid_confirmed。自己的B02取得有效目标余额后，余额刷新才succeeded；自己的任务failed/cancelled沿用原失败终结，付款前缓存可保留但不能据此宣称刷新成功。读取学校余额不保证充值已入账，仍不做本地余额加法。临时依赖错误、已有任务终态映射、付款回查和页面轮询沿用原规则。

本轮未处理问题5的“受理前绑定失效仍持续重试”，也未修改问题6的缴费列表入口超时。无公开或内部API字段、数据库迁移、Secret或部署配置变更；前端页面结构与文案不变，仅同步版本元数据。
