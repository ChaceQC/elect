# 七容器核心组合实施

日期：2026-10-05（Asia/Shanghai）。本轮按用户批准方案实施，目标为空闲约700 MiB，目标不是已验证结果。

0.19.5的R3分派诊断已接入：直接调用与独立HTTP保留相同身份/DTO边界，并以领域、登记路由和已验证请求ID定位脱敏异常，见[运行手册](../runbooks/后台健康与协调退出.md)。健康与协调退出尚在本阶段实施，不将旧探针503视为进程恢复。

## 范围和顺序

1. 固定0.18.3、13容器基线及统计口径。已有空库基线平均1336.08 MiB，详见[WSL记录](../runbooks/WSL部署与内存.md)；新增测量使用同一Docker工作集口径，OCR预热与工作峰值另列。
2. MySQL第一轮保留128 MiB Buffer Pool、40连接和临时表预算，日志缓冲改16 MiB、MyISAM key buffer改1 MiB，限制Performance Schema容量且保留诊断；Nginx固定1个worker。保留事务刷盘、binlog与备份恢复边界。
3. 新增核心进程入口，合并Gateway、Identity、Room、Monitoring、Payment、Notification控制、Audit及各自后台。七领域代码、数据库账号、连接池、事务、Outbox/Inbox、租约与恢复保持独立。
4. 邮件Worker使用无Web应用/路由的运行上下文；构建时生成迁移版本清单，运行时只核对数据库版本。
5. 新增`core`部署模式：core、school-adapter、mail-worker、mysql、rabbitmq、redis、nginx，共7个常驻容器、3个常驻Python进程。迁移、备份、状态检查为一次性容器。保留13容器`combined`及原独立模式。
6. 验证原卷双向升级、恢复关闭后台、权限/持久任务/故障语义及CI；记录空闲、OCR、集中监控与页面/合成支付邮件恢复峰值，列明未验收范围。

## 不变的业务与安全边界

- 核心内部使用进程内调用，复用现有服务身份/权限、参数与返回DTO校验及领域业务入口，不跨库查询。Gateway本身不拥有数据库。
- 核心与Adapter、邮件Worker与核心继续走认证HTTP及TLS。保留原服务签名身份与Secret，不把调用方身份替换为全权core身份。
- 核心共享进程意味着故障同时影响多个领域，进程也能读取这些领域的Secret；数据库账号隔离只保留代码误用防护，不再宣称进程级隔离。
- 保留签名事件、提交后发布、Inbox去重、提交后ACK、独立心跳、发送许可、单发送槽、unknown不盲目重发及学校并发限制。
- 第一轮保持combined各池2+1，8个应用池上限24连接。OCR仍延迟加载/单线程，其空闲子进程回收另行评估，不提前计入收益。
- 切换和回退先停止本项目全部旧应用与后台角色，再迁移并分阶段启动；禁止两种组合同时消费。恢复最后覆盖并关闭所有profile的后台和外发，不读取真实学校/邮件凭据做合成验证。

## 验收口径

空闲目标约700 MiB，包括正常后台扫描，不包括WSL、Docker守护进程或构建。规划预算为核心180、Adapter未加载OCR110、邮件60、MySQL230、RabbitMQ100、Redis与Nginx16 MiB；MySQL第一轮目标240–290 MiB，后续是否将Buffer Pool降至64 MiB依据实测，不自动采用。

工作峰值单独记录，覆盖OCR、50个监控到期、页面查询与合成支付/邮件故障恢复；要求无OOM、无重复副作用、无持续积压。合成验证不等同真实学校/SMTP/支付验收，短时测量不等同2核2GB/50人24小时容量验收。

当前状态：代码、7容器启动、MQ降级/恢复、13容器回退与合成50监控已验证；空闲7次采样平均577.39MiB。完整范围见[验收记录](../acceptance/七容器核心组合验收.md)，最新提交CI状态以PROJECT_PROGRESS.md为准。真实学校工作峰值与目标机长期容量未验收。
