# 查询额度、间隔与并发改进方案

日期：2026-11-11（Asia/Shanghai）。源码基线：dev `a1e17bf`，产品版本0.23.3。0.23.4已实施查询额度、等待提示及跨账号并发调整；同账号两路只读、15分钟定时、D04跨页面退避与B02的retry_after传播仍待后续实施。现有部署未升级。

## 目标与结论

用户反馈各种查询的总额、间隔和并发上限都过严。本轮覆盖余额、历史同步、手动采集、采集列表快照、寝室筛选、学校缴费列表及共同学校出口。限制既包括新请求记录预算，也包括真实学校执行并发，必须分别调整；提高每日额度不能解决30秒冷却和账号串行造成的等待。

本批放宽用户查询预算、缩短余额冷却并扩大跨账号执行能力；同账号两路只读留待独立实施。下述数值是本系统额度，不是学校确认的限制或已测得的容量。

同键重放仍不扣额度，新键合并仍计入提高后的请求记录预算，避免执行合并后无限新增持久映射。付款后余额刷新保留独立新鲜读取及原系统额度，二维码、认证、学校写与邮件预算不随公共默认值被顺带修改。

## 同账号并发与实际资源约束

现有账号锁不只是性能开关，同时保护认证单飞、缓存token恢复、学校写互斥和B02观测序号。第二批建议改为同账号最多两路读取，其中B02至多一路，认证与学校写独占；Room允许B02类与历史类并行。2026-11-11按用户“应该可以改为并行的”补充了下节具体方案；本轮仅完成评估，业务实现仍为账号串行。若仅扩大不同账号并发，余额和历史仍会互相等待。

账号锁和全局槽当前都会按100毫秒轮询等待，满载并非立即返回429。账号锁等待至预算用尽可能表现为本系统429/3秒，也可能先被外层超时转换为504。改善并发不能只把错误改名或继续延长等待。

D04整体45秒、最多50页，但每页单独取得并释放账号锁，单页预算最多20秒，不能误写为整份列表持续持锁45秒。C02单次读取最多40秒，监控B02单次读取预算可达约85秒；它们仍可能使其他查询等待。进入明细页会同时发起余额、历史和D04，后台采集也可能碰上该账号锁；这是源码可达路径，本轮没有现场竞争测量。

core各领域数据库池仍为2+1、等待3秒；网络请求前释放领域事务，因此3条数据库连接不等于只能并发3条学校请求。四槽需要定向核对领取、心跳、续租和页面读的连接等待，不能据静态推算声称已完成容量验收。core的数据库池环境参数同进程共用，不能声称只调环境变量就能单独扩大Room池。

内部ServiceClient每领域上下文共享12连接；学校HTTP的5连接限制属于每次读取创建的client/transport，并非跨请求共享上限，不会天然把全局10槽卡回5。集中token失效时，OCR仍只有一个计算线程和两个等待者，提高查询出口不等于扩大认证恢复能力。

### 同账号两路读取的具体方案（尚未实施）

普通学校查询每次创建独立HTTP client，使用Bearer token，不复用CAS CookieJar，具备在本系统内并行执行的基础；学校是否支持同token稳定并发仍需真实只读核对。起始并发取2，沿用全局10/后台8及Room四槽，先解决单用户不同查询互相阻挡的问题。

| 组合 | 建议执行方式 | 依据 |
| --- | --- | --- |
| B02余额/绑定读取 + C02历史 | 可以并行 | 读取不同数据，历史不必占住余额执行机会 |
| B02或C02 + D04缴费列表 | 可以并行 | D04每页领取读取许可，页与页仍按原规则顺序执行 |
| 两个B02，包括监控、手动刷新及绑定确认 | 继续有序 | 观测序号在响应后分配，不能仅靠现有序号判断两个并发响应的新鲜先后 |
| Room同owner两个历史窗口 | 继续有序 | 不同sync可部分重叠，学校返回后按日期范围替换历史，提交锁本身不能确定学校结果新鲜先后 |
| 认证、token恢复或学校写 + 其他学校操作 | 取得独占许可 | 复用认证结果，协调token发布与单次写入边界 |

#### Adapter共享许可

在SharedStore中复用现有全局槽的Redis双ZSET模式，为同一学校账号维护总读取集合与B02集合。一次Lua完成清理过期成员、检查原账号独占门、检查总读取数小于2及B02数小于1，全部满足才登记同一随机成员。B02等待者不能先占住总读取许可，否则余额排队仍可能堵住历史。许可由`read_bound`显式选择，不能把所有GET都推断为无副作用读取；D03即为可能建单的GET，仍不开放。

认证和学校写先取得原account_lock作为独占门，阻止新读取，再等已有读取排空。保持账号许可在前、transport内的全局槽在后，避免占着学校全局槽等待同账号。沿用110秒账号租约、原单调时钟deadline及按持有者释放；读集合清理和释放保持原子，不新增通用锁框架、环境参数或数据库表。

读取快路径在取得许可后读取当前凭据和token缓存，直接发出查询。缓存未命中或首次token失效时，先释放读取许可，再取得独占许可；在独占内复查当前凭据及缓存，已有较新token就复用，否则仅执行一次后台认证。恢复后重新取得读许可并读取当前token，不发送等待前保存的旧值。整个过程共享原deadline和重放预算，代理替换仍至多一次。

第二次失效的现有分支会标记requires_reauth并删除token缓存。并行后需在独占内复核当前凭据版本、状态及失败token，不能让迟到的旧token失败清掉其他请求已经刷新的缓存，也不追加无界重试。B02最终成功或失败的observer都保留在B02许可内，认证恢复期间先退出许可，重试时重新取得。

显式认证的激活及缓存发布也应纳入相同协调。现有activate在版本提交后才写暂存token，同一激活重放也会再次写入，可能覆盖同版本已刷新token；这是并行改动前已经存在的可达路径。单独作为一个小步核对激活重放复用和缓存发布，不能把版本校验误当成对同版本token的保护，也不扩展到无关认证流程重构。

#### Room领取与结果顺序

保留owner偏好行的短事务锁和`FOR UPDATE SKIP LOCKED`，将统一IDLE条件改为两类空闲条件：

- B02类：binding_sync与balance_refresh合计至多一个有效租约。
- 历史类：同owner至多一个有效历史窗口，可与B02类同时持租。

候选预筛与锁内复核必须使用同一分类规则；`claim_operation`和`claim_history`均传入类别，保持偏好行在前、任务行在后的锁顺序。每类32个候选与独立轮转游标继续使用。一个owner最多占两个Room有效执行租约；租约过期接管时旧网络调用可能仍在途，实际学校并发仍由Adapter许可约束，不能把租约数当作物理请求数。

付款后刷新仍为独立B02根任务，等待已有B02后执行，Room的历史租约不再单独阻止它被领取；Adapter账号总读取或全局槽满时仍可能排队。保留固定订单键、created_at/id领取顺序、旧支付别名独立化和原系统预算。所有B02从发出查询到成功/失败观测序号分配保持账号内有序，Room继续拒绝较低序号写入。历史保留45秒租约、10秒续租、90秒执行预算及lease_owner/epoch提交栅栏，不新增历史取消能力。

## 等待时间与前端反馈

- 分钟预算按最早仍占窗口的记录计算剩余时间，不统一再等60秒；多项同时限制时以足以解除已知时间限制的较长等待为准。
- 仅待办满时提示等待已有任务完成，快照数量及成员总量满分别提示等待回收，不承诺固定时间后一定可用。单份记录过多直接说明缩小范围，不可重试且不附固定等待。
- 学校真实HTTP429会发布全局1至3600秒共享冷却，缺省30秒；后续请求返回Redis剩余TTL。真实学校限流的作用范围尚未确认，保留共享冷却，不因本系统额度放宽而绕过。
- 前端保留服务端具体原因并附重试秒数，避免把所有429改写成“请求额度暂不可用”。保留原幂等键与退避截止时间，普通列表、缓存和操作进度读取不额外套上学校新请求额度。
- D04的退避目前只在组件状态内，切换寝室/日期、离页或重载可能丢失；建议按账号与该查询能力保存截止时间，自动及手动入口都遵守。不要把某类本地额度用完错误扩大成所有查询的共同冷却。
- 异步B02观测目前会丢失上游retry_after；后续单独补齐其等待信息传播，保留余额新鲜度与付款后独立读取语义。

## 定时监控间隔单列

监控定时间隔当前为60至1440分钟，与手动查询冷却是独立规则。若后续把可选下限放到15分钟而默认仍为60分钟，需同时处理监控配置和样本的数据库CHECK、Monitoring及Room DTO、前端与生成契约，并把代理小时合批改为能表达15分钟逻辑槽的批次规则；仅修改输入框不能得到每15分钟实际采样。提醒冷却继续按间隔减2分钟，23:00至06:00静默边界保持。本轮先记录范围，不把该迁移与查询429修正捆绑。
