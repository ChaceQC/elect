# 查询额度、间隔与并发改进方案

日期：2026-11-11（Asia/Shanghai）。源码基线：dev `a1e17bf`，产品版本0.23.3。状态：源码排查与建议，未实施业务改动，未改变现有部署。

## 目标与结论

用户反馈各种查询的总额、间隔和并发上限都过严。本轮覆盖余额、历史同步、手动采集、采集列表快照、寝室筛选、学校缴费列表及共同学校出口。限制既包括新请求记录预算，也包括真实学校执行并发，必须分别调整；提高每日额度不能解决30秒冷却和账号串行造成的等待。

建议先放宽用户查询预算、缩短余额冷却并扩大跨账号执行能力，再独立实现同账号两路只读。以下数值是一组可实施的建议起点，不是学校确认的限制或已测得的容量。

## 当前规则与证据

| 路径 | 当前限制 | 正常使用受到的影响 |
| --- | --- | --- |

## 建议调整值

| 项目 | 建议值 | 配套行为 |
| --- | --- | --- |
| 浏览器余额新请求 | 30次/分钟、600次/24小时、32个非终态 | 冷却30秒降到5秒，按最近成功读取计算实际剩余秒数；失败不再额外触发成功冷却，真实学校429仍遵守原截止时间 |
| 历史同步新请求 | 20次/分钟、120次/24小时、32个非终态 | 未完成sync从2放宽至4，待处理窗口从64放宽至128；沿用窗口级公平领取及原范围 |
| 手动及配置立即采集 | 20次/分钟、240次/24小时、32个非终态 | 两种入口继续共用预算，配置受理仍须原子提交；定时任务不扣用户额度 |
| 采集快照 | 创建30次/分钟、每owner48个 | 保留单份20,000条及成员总量60,000的空间预算；数量和成员量分别提示，超过单份范围明确要求缩小日期 |
| 寝室候选及筛选 | 候选5次/秒、筛选10次/秒 | 保留账号归属及原查询结果校验 |
| 学校出口 | 全局10槽、后台8槽 | 保留共享租约及总deadline；满载仍在原预算内等待，预留2槽供前台认证链路 |
| Room与监控执行 | Room查询4槽，监控直连/代理均4槽 | Payment回查暂保留2槽；公共read_slots须由调用点选择数量，避免改公共常量顺带扩大其他角色 |
| 同账号只读 | 目标2路，只读与认证/学校写分开协调 | 作为独立实现，不直接把现有账号锁改成2个许可，详见下一节 |

同键重放仍不扣额度，新键合并仍计入提高后的请求记录预算，避免执行合并后无限新增持久映射。付款后余额刷新保留独立新鲜读取及原系统额度，二维码、认证、学校写与邮件预算不随公共默认值被顺带修改。

## 同账号并发与实际资源约束

现有账号锁不只是性能开关，同时保护认证单飞、缓存token恢复、学校写互斥和B02观测序号。建议第二批实现共享的账号读写协调：缓存token有效时最多两路只读，认证与学校写取得独占许可；token失效时释放读取许可再进入原认证单飞，其他读取复用恢复结果；B02继续遵循持久观测序号和旧结果不得覆盖新结果的规则。Room领取中的同owner互斥也须配套调整，否则Adapter支持两路后，余额和历史仍无法并行。若首批只扩大不同账号并发，必须明确同账号串行仍存在。

账号锁和全局槽当前都会按100毫秒轮询等待，满载并非立即返回429。账号锁等待至预算用尽可能表现为本系统429/3秒，也可能先被外层超时转换为504。改善并发不能只把错误改名或继续延长等待。

D04整体45秒、最多50页，但每页单独取得并释放账号锁，单页预算最多20秒，不能误写为整份列表持续持锁45秒。C02单次读取最多40秒，监控B02单次读取预算可达约85秒；它们仍可能使其他查询等待。进入明细页会同时发起余额、历史和D04，后台采集也可能碰上该账号锁；这是源码可达路径，本轮没有现场竞争测量。

core各领域数据库池仍为2+1、等待3秒；网络请求前释放领域事务，因此3条数据库连接不等于只能并发3条学校请求。四槽需要定向核对领取、心跳、续租和页面读的连接等待，不能据静态推算声称已完成容量验收。core的数据库池环境参数同进程共用，不能声称只调环境变量就能单独扩大Room池。

内部ServiceClient每领域上下文共享12连接；学校HTTP的5连接限制属于每次读取创建的client/transport，并非跨请求共享上限，不会天然把全局10槽卡回5。集中token失效时，OCR仍只有一个计算线程和两个等待者，提高查询出口不等于扩大认证恢复能力。

## 等待时间与前端反馈

- 分钟预算按最早仍占窗口的记录计算剩余时间，不统一再等60秒；多项同时限制时以足以解除已知时间限制的较长等待为准。
- 待办满、快照存量满应说明等待已有任务完成或快照回收，不能承诺固定60秒后一定可用。单份记录过多应直接说明缩小范围，等待不会解决。
- 学校真实HTTP429会发布全局1至3600秒共享冷却，缺省30秒；当前后续请求固定回传30秒，应改为Redis剩余TTL。真实学校限流的作用范围尚未确认，保留共享冷却，不因本系统额度放宽而绕过。
- 前端保留服务端具体原因，避免把所有429改写成“请求额度暂不可用”。保留原幂等键与剩余倒计时，普通列表、缓存和操作进度读取不额外套上学校新请求额度。
- D04的退避目前只在组件状态内，切换寝室/日期、离页或重载可能丢失；建议按账号与该查询能力保存截止时间，自动及手动入口都遵守。不要把某类本地额度用完错误扩大成所有查询的共同冷却。
- 异步B02观测目前会丢失上游retry_after，余额失败后还可能遇到30秒本地冷却；后续单独补齐其等待信息传播，保留余额新鲜度与付款后独立读取语义。

## 定时监控间隔单列

监控定时间隔当前为60至1440分钟，与手动查询冷却是独立规则。若后续把可选下限放到15分钟而默认仍为60分钟，需同时处理监控配置和样本的数据库CHECK、Monitoring及Room DTO、前端与生成契约，并把代理小时合批改为能表达15分钟逻辑槽的批次规则；仅修改输入框不能得到每15分钟实际采样。提醒冷却继续按间隔减2分钟，23:00至06:00静默边界保持。本轮先记录范围，不把该迁移与查询429修正捆绑。

## 实施拆分与验证

1. 先修余额5秒成功冷却、分钟预算剩余时间、学校冷却TTL和具体错误文案；用现有相关用例定向验证冷却边界、失败后重试、原键恢复。
2. 分别调整余额/历史、手动及配置采集、快照/筛选的调用点阈值，保持同owner事务和有界持久记录；只检查新旧边界、满额拒绝无残留及配置原子性，不重复全量测试。
3. 扩大学校出口到10/8、Room到4槽、监控到4/4；在隔离合成场景检查4个不同账号可推进、全局实际占用不越界、原租约续期与退出，核对已有池等待日志。
4. 独立实现同账号两路只读及Room领取协调，定向覆盖余额/历史并行、并发token失效只认证一次、学校写独占及旧B02结果不覆盖新结果；学校真实同token并发尚待指定只读核对，不将合成结果当成该事实。
5. 如实施15分钟定时监控，再单独交付迁移、跨域契约和代理批次规则；不通过删旧样本、旧幂等记录或改写历史事实释放额度。
