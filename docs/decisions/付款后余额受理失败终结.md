# 付款后余额受理失败终结

日期：2026-10-08（Asia/Shanghai）。版本：0.22.6。仅修复本轮全仓审查问题5，保留问题1—4修复；问题6未处理。现有部署本轮不升级。

## 问题与规则

学校确认付款后，Payment以固定订单键向Room受理余额刷新。若本人绑定已不存在或同步为inactive，Room在创建任务前返回404 NOT_FOUND；原实现把这条明确业务失败也转换为unavailable，随后继续pending，每30秒重新受理，页面一直等待。

Payment现在按阶段和明确错误分类：尚无balance_refresh_operation_id，且受理返回404 NOT_FOUND时，余额刷新记为failed，保留NOT_FOUND、空operation关联，并由既有终态提交清空next_check_at及回查租约。付款事实仍为paid_confirmed，不能因为余额刷新失败撤销学校已确认的付款，也不据此重新建单或推算余额。

| 场景 | 余额状态与后续行为 |
| --- | --- |
| 尚无operation，Room受理返回404 NOT_FOUND | failed，结束自动回查，原付款事实保留 |
| 尚无operation，429限流、503依赖故障 | pending，保留错误，30秒后按同订单固定键重试 |
| 尚无operation，409 OPERATION_IN_PROGRESS | 解绑尚在确认，仍pending/30秒重试；不能仅凭retryable=false终结 |
| 已有operation，状态查询返回404/503等错误 | 保留operation和pending，30秒后继续读取原任务 |
| 原任务返回failed/cancelled | 沿用既有failed终结与停止调度 |
| 原任务返回succeeded | 沿用既有succeeded终结，不保证余额已经增加 |

本次不新增通用错误分类器，也不把所有4xx都当成业务终态。Room受理继续先查固定键，再检查绑定，因此已受理但响应丢失的原任务仍可重放取回；问题4的付款后独立B02、owner串行与系统6/60/8预算保持。

## 恢复与页面

- 旧paid_confirmed/pending/无关联记录无需迁移，下一轮正常回查重新得到绑定失效404后即终结。只依据本次Room响应，不以历史error_code直接改写存量。
- 订单提交继续使用原有效回查租约与操作→订单锁顺序，保留已确认付款不能倒退的规则。失败终态不会被正常领取器重新激活，重启也不重复受理。
- 前端已按failed停止付款余额轮询，并展示“支付已确认，余额刷新失败；请在寝室页面重新查询余额。”，无需新增页面状态或按钮。重新绑定或手动查询不改写旧订单的刷新结果。
- 无公开/内部API字段、数据库迁移、Secret、资源池或部署配置变更；仅同步版本元数据及既有CI定向测试入口。
