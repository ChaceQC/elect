# 监控配置采集统一计额

日期：2026-10-08（Asia/Shanghai）。版本：0.22.3。仅修复本轮全仓审查问题2，保留问题1修复；问题3—6未处理。本轮不升级现有部署。

## 问题与选择

原PATCH /monitor修改interval_minutes后提升generation、取消旧代次并把next_run_at改为当前时间。Scheduler随后创建新任务，但不写monitor_run_requests，反复60↔61分钟即可绕开手动采集预算；旧代次任务也无法合并这些请求。

保留开启监控和修改间隔后的立即采集，统一计入已有用户采集额度，避免为配置另开一个独立限额。正常定期调度继续遵循计划。

## 受理与事务边界

- 仅当保存后状态为active，且enabled或interval_minutes发生实际变化时，本次配置触发立即采集。关闭、无变化保存、阈值/邮箱/次数调整以及requires_reauth/blocked_room下的不可执行间隔设置不新增采集计额。
- 配置与手动采集在同一owner的monitor行锁内使用相同预算：每分钟6次、滚动24小时48次、最多8个非终态请求映射。更换generation或开关监控不清空计数，合并到已有run的手动新键仍计额。
- expected_version、参数与控制状态检查保持。无变化保存不改代或计额；旧版本返回409，不重复创建任务。PATCH响应丢失后先GET核对，沿用原版本协议。
- 预算检查先于invalidate。超额返回429/RATE_LIMITED与Retry-After，原配置、版本、generation、计划、运行和提醒状态不变。关闭不会因额度耗尽而被拒绝。
- 配置改代、原栅栏失效、立即run、唤醒Outbox和请求映射在同一本域事务提交，任何一步失败全部回滚；不在事务内访问学校或MQ。复用已有monitor_run_requests索引、180天保留和归档机制，内部键包含不可通过浏览器请求头传入的NUL分隔符，按monitor及generation区分，不新增API字段或迁移。

## 调度与恢复

立即run的scheduled_for使用本次数据库计划锚点，next_run_at同时推进到锚点加新间隔。Scheduler在下一正常槽前不会再创建一次立即run，后续只改阈值/邮箱等也不会留下刚刚受理时的到期槽。

立即任务沿用原Worker、持久扫描、Outbox、租约、generation/epoch和学校并发限制；重启继续读取已有run和计额映射。正常定期Scheduler不写用户请求映射，也不会因用户额度耗尽停止计划。失效旧代次及在途取消边界保持。
