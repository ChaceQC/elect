# T4 查询与持久采集

更新日期：2026-10-01；状态：实施中。

按总计划先完成 P4 查询，再接通 P5b 运行和 F4/F5-05。学校只读联调可使用本地 auth.txt；本阶段不执行学校绑定、支付或 SMTP。

- B02 手动刷新是持久 Room 操作，按账号合并、30 秒冷却；更新所有现存本人绑定的余额缓存，不创建采集样本。失败保留最后成功值及取得时间。
- C02 按最多 7 天的非重叠窗口推进，同账号最多一个在途历史窗口。使用授权绑定映射的 school_room_id 作为 buildId，不依据响应行 buildId 改变归属。范围最多 366 天，上海日期含首尾，禁止未来日期。
- 当前未确认学校稳定来源 ID 或完整覆盖语义，因此每个成功窗口以内容快照替换该范围，保留同内容多行的 occurrence_index；空响应不补零，覆盖度不升级为 complete。失败窗口保留原成功记录。
- Scheduler/Worker/恢复器以 MySQL 为权威，学校请求在事务之外执行；运行以 generation/binding/credential_version/epoch/有效租约共同验证。T4 首批采集采用 balance_only。
- 样本分页持久固定成员 ID，TTL 30 分钟；关闭监控后历史仍可读。趋势显示学校记录金额，余额差显示本次减上次。

新增模块按查询、受理、任务领取、结果提交、聚合与前端展示拆分，复用既有认证、监控控制和可靠事件设施。必要的既有改动限于路由注册、服务权限、运行编排和文档状态。

第一批查询验收已通过；用户特别要求同账号不同寝室的余额不混用，B02缓存与采集入口均按学校roomId精确匹配，缺失目标保持失败/旧缓存。
