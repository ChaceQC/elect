# 建单凭据失效与发送边界

日期：2026-10-08（Asia/Shanghai）。版本：0.22.4。仅修复本轮全仓审查问题3，保留问题1、2修复；问题4—6未处理。现有部署本轮不升级。

## 问题与处理

Payment按受理时的credential_ref/credential_version保存订单。排队期间重新认证使版本变化，原Adapter在创建发送台账之前抛出SCHOOL_REAUTH_REQUIRED；Worker将错误保留为reconciling，再次执行仍携带旧版本，没有学校订单可回查，也不能释放未解决槽。

由拥有发送事实的Adapter持久化明确拒绝，Payment复用已有rejected订单终态与failed操作。保留订单受理时的版本，不自动改用新凭据发送旧订单，也不由Payment根据一个错误码猜测学校是否已接收。

## 事务与发送边界

- prepare仍先锁定本人凭据并核对引用、版本、active状态及use_allowed。仅捕获这一检查的SCHOOL_REAUTH_REQUIRED；数据库/依赖故障继续抛出，不伪造拒绝。
- 同一事务继续锁定upstream_operation_id。既有记录必须匹配owner及请求摘要，原状态优先，凭据失效不能覆盖confirmed、dispatched、unknown或原拒绝，也不能复用他人或不同内容的上游编号。
- 没有台账时，凭据有效写prepared，凭据失效写rejected与SCHOOL_REAUTH_REQUIRED；upstream_operations和adapter_payment_orders密文原子提交，dispatched_at保持null。写入失败全部回滚，重复调用读取同一台账。
- prepared后的凭据变化仍在发送前阻断。settle取得台账行锁后重新核对state=prepared且dispatched_at为空，才将发送前凭据/不存在错误终结；不使用锁外快照决定拒绝。
- 已标记dispatch后的错误、响应丢失或学校结果不明继续保持unknown，保留原台账及未解决槽。已验证的学校明确拒绝沿用原处理，不改变D01一次发送与E01–E04规则。

## Payment恢复与用户行为

Worker收到持久rejected后沿用现有逻辑：订单rejected、建单操作failed、释放租约，生成列自动释放未解决绑定槽。后台不再领取该操作，也不再为该订单安排学校回查；用户无需先手工停止处理，可以使用新幂等键重新建单。原键始终返回原订单及拒绝终态，不自动重建。

升级后，旧submitting/submit_unknown及reconciling操作使用原upstream_operation_id继续执行。若确无台账且凭据已失效，创建持久拒绝后结束；拒绝响应丢失或执行器重建时仍从台账恢复。已发送订单不会因此释放占位。通用ApiError/超时继续沿用Worker恢复逻辑，不新增批量维护命令或存量改写。
