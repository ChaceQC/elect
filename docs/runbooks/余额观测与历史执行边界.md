# 余额观测、历史执行与支付余额终态

适用源码0.19.4，日期2026-10-06（Asia/Shanghai）。专项证据见[R2验收](../acceptance/审计修复/R2执行时间与终态边界.md)。现有部署不自动升级。

0.19.5已在R3接通本页OCR fatal到进程协调退出，并验证不可结束原生线程的最终退出保障；当前健康与停止预算见[后台健康与协调退出](后台健康与协调退出.md)。下文R2阶段的未完成标记保留为历史边界。

## 升级与回退

统一升级先停止本项目所有旧profile角色，再执行Adapter `school_0007`、Room `room_0006`；其余五域head不变。原Secret、连接和学校5/4/1配额、七领域边界不变。内部余额DTO须一起升级，禁止混跑新旧写者。迁移只建表/加可空列，不隐式扫描修复业务数据。

旧缓存`observation_sequence=NULL`表示排序未知的旧基线；保留金额和原时间但显示stale，首次有效新观测可覆盖。Adapter计数表不能清空、用凭据版本替代或单独回滚。恢复须保留Adapter计数与Room缓存高水位：0.20.1的恢复apply在七域隔离后自动分批核对，缺失或倒退时拒绝完成且不修正数据，见[集成恢复手册](审计修复集成与恢复.md)。单独回退Adapter库可能导致较小序号被拒绝，应保持停写并核对同一完整备份集，不关闭顺序判断。

回退先停止领取，等待/取消在途窗口，确认旧执行不能提交后切换。扩展字段可保留，不逆向恢复已修正金额/终态。旧镜像缺少执行/顺序边界，需保留补丁或暂停相关自动任务，不能只回滚镜像后继续写。OCR可暂停自动识别并保留人工验证码；取消Future不能终止原生线程。

## 余额契约

`/rooms/bound`返回`items`和`observation`，后者含`sequence`、`observed_at`、`request_id`、`source=school_bound_rooms`、`error_code`。在账号串行边界内、学校结果返回后记录时间，以短事务分配序号。结构错误/明确读取失败也可生成有序错误；拿锁、凭据或整体deadline等未获得可靠观察的错误仍用错误信封，不伪造序号。

调用者先查`observation.error_code`，错误时不将空items解释为成功空绑定。手动B02、同步镜像、监控回写和新绑定确认共用Room仓储。旧绑定台账没有序号时只确认绑定，不重新把旧余额标fresh；后续B02新观测更新缓存。

`/controls/balance-observed`接收`binding_id`、可空`amount`及同一观测元数据，不再接收调用方临时生成的fetched_at。低序号忽略；同序号同内容幂等，冲突返回VERSION_CONFLICT并记脱敏日志，不覆盖缓存。新失败保留最后成功金额/时间并存错误序号/时间/代码，新成功解除stale。无金额保持未知，不补零；旧错误不降级新成功。列表同步失败单独显示，不据此改写较新的余额质量。

公开Balance结构不变：`fetched_at`是最后成功取得学校余额的Adapter观测时间；`school_observed_at`仍只使用学校明确提供的时间，未知null。入库延迟、相同时间及系统时钟回拨不决定覆盖顺序。

## 历史执行

每窗口90秒单调deadline，覆盖目标回查、内部/账号/学校槽等待、读取、解析、入库锁等待和提交。内部`HistoryExecutionQuery.budget_seconds`传递剩余预算，学校读取最多40秒（单读20秒）；ServiceClient budget同样约束HTTP和core直接调用。

租约45秒，每10秒按窗口ID、owner、lease_owner、execution_epoch及未过期条件续期，不增加业务版本。获取锁后重新读数据库时间，防止锁等待期间过期却被复活。失租立即取消等待，旧epoch不能提交。最终事务持有有效窗口行锁后由锁阻止接管；每批最多250行SQL，整个成功窗口原子替换，中途失败回滚旧记录。总deadline到期后不另加执行预算，原租约到期后按最多3次尝试接管。

Room循环移除多个串行工作共用120秒超时，改为工作单元预算、单元间检查停止信号；原125秒退出预算保持，其他领域checked_tick不变。R3再统一健康成功扫描/在途租约语义。

## 支付失败余额与旧调度维护

0.22.5起，Payment确认付款后受理的余额任务独立执行B02，不复用已有查询；同owner当前读取结束后由原领取器执行，同订单原键重放不增加任务。旧未终结的payment合并别名不再继承根结果，领取时按原ID恢复独立读取，既有历史终态不重写。升级按既有流程停完旧Room角色后统一切换，不混跑新旧终态传播者；无需新迁移或维护apply。详见[付款后余额独立读取](../decisions/付款后余额独立读取.md)。受理前绑定失效的无限重试属于本轮审查问题5，本补丁未处理。

paid_confirmed仅领取余额pending。原operation succeeded或failed/cancelled后清空next_check_at，保留付款事实和原operation。读取暂时失败保留pending/错误，30秒重试；业务pending仍2秒到期。寝室页手动查询不改变旧自动刷新的真实结果，也不新建订单。页面原有失败反馈和停止轮询符合规则，无新增按钮或布局。

旧`paid_confirmed + failed + next_check_at`在独立维护窗口审查，先停Payment回查，保持Room只读API可用。命令使用本领域运行身份，只查关联Room operation，不查学校、不新建任务、不删除订单：

```sh
python -m services.payment.repair_balance_refresh --batch-size 50 --batches 1
python -m services.payment.repair_balance_refresh --apply --batch-size 50 --batches 1
python -m services.payment.repair_balance_refresh --apply --after <上次after游标> --batches 1
```

默认dry-run；每批1..100条，默认50条/1批，最多100批。只输出分类计数、游标、是否扫完。可证失败/取消清调度，仍运行恢复pending，可证成功记succeeded；缺失/404/503或无法确认保持原数据并列unconfirmed。应用时核对版本和有效租约，变化行跳过，每单独立事务、重跑幂等。游标之前的unconfirmed需从头复查，不能以exhausted宣称全修复。生产apply需对应环境维护窗口授权，本轮只做隔离合成验证。
