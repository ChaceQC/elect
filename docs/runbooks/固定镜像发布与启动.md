# 固定镜像发布与分阶段启动

0.19.0支持`ELECT_DEPLOYMENT_MODE=core`，其后端固定摘要校验以core为基准；启动顺序为基础服务→迁移→Adapter→core→mail-worker→Nginx。切回combined同样先停止全部旧角色，保留原卷与Secret。发布部署包包含core与恢复覆盖，只有local模式加载core-build；默认模板不开放真实副作用。7容器不含可选SMTP出口代理及一次性作业，详见[核心组合](../decisions/七容器核心组合.md)。

日期：2026-10-04（Asia/Shanghai）；版本：0.18.0。开发版镜像交付，不代表T8或2核2GB/50人24小时验收；第五步页面刷新和留存清理仍待实现。

## CI发布边界

CI第一轮前后端分别构建runtime和test/browser-test，打包公开来源清单后供三组隔离验证复用。标签发布作业依赖五组全部成功的check，核对本次检出提交、版本、包SHA-256、镜像ID和OCI标签后只加载runtime；镜像传输使用Actions artifact，不包含Secret/业务卷/浏览器会话。缓存仅加速构建，不复用测试结果。完整覆盖与计时见[CI决策](../decisions/CI并行验证.md)。生产启动次序保持不变。

在dev完成可验证提交后推送`vX.Y.Z`标签，前后端工程版本必须一致且与标签相同。`容器验证 / check`完成本次单元/契约/浏览器、空库、原卷、故障及加密恢复检查后，才登录GHCR并发布`ghcr.io/chaceqc/elect-backend:vX.Y.Z`和`elect-frontend:vX.Y.Z`。发布直接使用本次空库集成实际受测的runtime镜像，不在测试后重新构建，不发布latest；已有不同镜像的版本被拒绝覆盖。

镜像包含OCI的source/version/revision标签。开发版GitHub Release和Actions artifact提供：

- `release.env`：完整公开配置模板，combined/published及前后端/基础服务固定sha256摘要；域名、证书和Secret路径仍为占位值，外部副作用默认关闭。
- `release.json`：版本、源提交、linux/amd64、实际镜像摘要和check运行链接，明确容量未验收。
- `deploy-vX.Y.Z.tar.gz`：仅Git跟踪的deploy文件及本手册；不含前后端源码、真实env、Secret、依赖或构建产物。

标签检查失败、取消或未完成时不会进入发布。当前交付平台为linux/amd64，其他CPU架构尚未验收。GHCR包若为私有，目标机先使用具备read:packages权限的账号登录`docker login ghcr.io`；凭据由Docker保存，不写入公开env或仓库。

## 首次空库

目标机只安装Docker Engine和Compose 2.24.4+，无需Node、Python、uv或源码。从[开发版发布](https://github.com/ChaceQC/elect/releases)下载三个资产，解压部署包，将`release.env`保存为绝对路径`stack.env`；填写ELECT_DOMAIN、ELECT_TLS_CERT_FILE、ELECT_TLS_KEY_FILE、ELECT_SECRETS_DIR，保留镜像摘要和ELECT_RELEASE_VERSION/REVISION。

从清单复制后端完整摘要引用，用该镜像离线provision：

```sh
mkdir -p /opt/elect/secrets
chmod 700 /opt/elect/secrets
# 从公开清单读取完整repo@sha256引用，不执行env内容。
task_image=$(awk -F= '$1 == "ELECT_IMAGE" {print $2}' /absolute/stack.env)
docker pull "$task_image"
docker run --rm --network none --user 0:0 \
  -v /opt/elect/secrets:/run/provision "$task_image" \
  python -m services.deployment.provision --output-dir /run/provision
sh deploy/start.sh /absolute/stack.env elect
sh deploy/status.sh /absolute/stack.env elect
```

provision拒绝已有非空Secret目录。正式证书由管理员配置；本轮仍不执行生产证书部署/更换。私网HTTP可按[本机手册](本机私网部署.md)配置公开选择字段，内部TLS仍保留；SMTP定向通道只在明确配置时启动，不自动使用本地邮件凭据。

启动入口校验公开配置及全部镜像摘要，逐个拉取，检查前后端实际版本/源提交相同；TLS和Nginx配置在停旧应用前预检。随后停止本项目已有全部非基础角色（包括旧profile角色、已关闭的可选通道），保留原容器退出宽限，再按以下顺序执行：

1. MySQL、Redis、RabbitMQ分别等待健康。
2. migrate一次性作业成功完成。
3. Adapter、Monitoring、Identity、Room、Notification、Payment、Audit、Gateway分别等待健康。
4. 当前模式的后台角色及可选SMTP通道，最后启动Nginx。

使用显式`--parallel 1`和`--no-build --no-deps`，不会隐式重跑依赖/迁移或构建。一次性TLS/迁移容器成功退出是正常状态。

## 已有卷升级与恢复

保留原项目名、Secret和命名卷，先按[加密备份](备份恢复与隔离对账.md)保存可恢复副本。下载新开发版文件，将配置中的镜像/版本/源提交替换为新清单，同时保留本机域名、路径、部署模式及已授权开关，然后执行：

```sh
sh deploy/upgrade.sh /absolute/stack.env elect
```

upgrade与首次start共用预检和串行启动。旧Secret尚未包含当前权限时，按[第四步升级](../decisions/Docker低资源执行效率.md)先停应用、离线重复upgrade_controls，保留原密码/密钥；0.18.0没有新增数据库迁移或Secret。既有standalone→combined切换会停止旧Worker/Relay，不重新provision、不删除卷。

拉取/配置/镜像标签/入口预检失败发生在停旧应用之前。迁移或后续健康失败立即停止后续阶段，已启动组件保留供检查，不自动回滚数据库；回退旧镜像须确认schema兼容，否则使用隔离恢复。status/backup/restore继续用同一公开env/统一compose入口；恢复覆盖始终最后应用，禁用后台且不加载host SMTP通道。

## 开发与隔离验证

源码开发使用`ELECT_IMAGE_MODE=local`和`compose.sh up -d --build`，构建入口由compose.build.yaml提供。生产start/upgrade拒绝local模式。

仅`elect-test-*`隔离项目可显式使用`--test`，允许已构建的本地镜像而不拉取registry；这不能冒充registry验收。`test-stack.sh`验证新空库，`test-image-delivery.sh`在相同项目/原卷中解出仅deploy的包，以published选择、无源码/无构建启动13容器。CI另通过标签发布验证实际摘要。

本机默认地址池耗尽时，可仅给本次隔离项目设置未占用的`ELECT_TEST_NETWORK_PREFIX=10.249`，选择compose.test-network.yaml的五个小网段；恢复另设`ELECT_TEST_RESTORE_NETWORK_PREFIX=10.250`。默认CI仍使用Docker自动分配，不修改全局地址池或清历史网络。
