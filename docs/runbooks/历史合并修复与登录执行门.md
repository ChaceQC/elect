# 历史合并修复与登录执行门

日期：2026-10-06（Asia/Shanghai）；源码版本0.19.3，审计执行计划R1（AUD-10/AUD-11）。现有部署升级与现有业务数据apply需另按目标环境授权执行，本轮仅在一次性MySQL中验证。

## 历史完成传播

`upstream_operation_id`是历史别名到直接主任务的稳定关系；`saga_step`仅描述阶段。首窗口后别名进入`read_school`，仍持续跟随主任务，全部窗口结束后传播成功或失败及错误码；窗口尚未完成或根任务没有窗口时不标成功，取消窗口不会标成功。

根操作必须为C02历史任务、没有上游且owner/绑定与sync一致；别名必须同owner、同type、同绑定/房间、不是自身、没有自己的sync。孤儿、多级、循环、错误归属不推测修复。已终结操作不反向改成running。传播在既有本人偏好锁事务内完成，释放8个非终态operation配额；速率、每日请求和窗口预算保持。

主操作按主键更新，别名按owner/type前缀检索并校验root，不使用跨全表的主键OR关联。已有`uq_room_operations_0(owner_user_id,type,idempotency_key_hash)`和`ix_room_operations_admission(owner_user_id,type,created_at)`可用，本轮不增加索引或迁移；七域迁移头不变。R4保留清理、R5查询优化仍为独立工作包。

## 存量命令

运行入口位于runtime镜像自带的`services.room.repair_history`，使用Room领域app身份，从既有`ELECT_RUNTIME_FILE`在内存读取配置，不打印连接串、账号、正文或摘要，也不调用学校。core环境应将该变量指向Room runtime，而不是Gateway/其他域配置。

先部署含修复的镜像；在维护窗口停止所有会写Room历史的旧worker及历史受理入口。保持原卷与Secret，不启动旧新worker混跑。维护命令一次只运行一个实例，不与迁移DDL同时执行。不在服务启动或Alembic升级中自动运行本命令。

在具有Room runtime、仅可达本项目MySQL的维护容器中执行：

```sh
python -m services.room.repair_history
python -m services.room.repair_history --batch-size 100 --batches 1
```

默认dry-run，不加锁、不更新数据。每批输出JSON：`mode`、`summary`中的候选/可修/等待/已修/冲突数量、`counts`分类，以及`after`游标和`exhausted`。游标是操作ID编码，只用于续扫；不输出账号、幂等键hash、请求摘要或学校内容。默认只扫一批、至多100条，`--batches`可显式设为1..100，避免无界运行。

审查输出并获得对应环境的apply授权后，**从起点重新扫描**，不能直接拿dry-run末尾游标开始apply：

```sh
python -m services.room.repair_history --apply --batch-size 100 --batches 1
python -m services.room.repair_history --apply --after <上一已提交批次的after> --batch-size 100
```

apply在每批独立事务内取得本人偏好锁、重新读取并审查别名。只修复主任务和sync终态一致、请求范围对应窗口完整且全部成功/失败、错误码一致的记录；保留ID、请求摘要、幂等hash、创建时间及原关联。已完成别名不会再次入选。批次失败不输出原始驱动异常，本批回滚；之前已输出的apply批次已提交，可从上次游标重试。人工保存脱敏JSON和目标镜像SHA作为维护进度，不保存Secret或数据库导出到Git。

分类含义：

| 分类 | 处理 |
| --- | --- |
| repairable | 全部证据一致；仅apply才写入 |
| waiting | 主任务或窗口仍运行；保留等待 |
| orphan_or_chain | 找不到直接根sync，包含孤儿或多级/循环；留待诊断 |
| relation_conflict | 根有上游、自关联、错误归属或别名有自己的sync；不写入 |
| window_conflict | 窗口与请求范围不完整对应；不写入 |
| terminal_conflict | 主任务/sync/窗口终态或错误码不一致，含取消窗口；不写入 |
| already_terminal | 候选读取后已被正常流程终结；跳过 |

`exhausted=true`仅表示本次扫描到末尾，不代表等待/冲突已解决。等待任务终结后可从零游标重跑。对异常关系先诊断，不能统一改成成功。无需DDL；若将来需要索引变更，必须独立迁移和验收，不能嵌入此命令。

## 登录执行门

每个Identity上下文初始化一个LoginSaga及执行门，最多1名持锁执行者、2名等待者；前台等待至多250ms，超限沿用429/RATE_LIMITED及3秒重试提示。取得门后才申请GET_LOCK连接；释放命名锁及连接后才归还门。学校认证/激活仍在SQL事务之外，内层事务与会话读取使用原业务池，不提高2+1池、MySQL或学校并发预算。

所有`locked()`路径共用此门，包括登录恢复和凭据撤回恢复；后台繁忙时不排队、不更改业务失败状态，下轮重试。前台429不替换原challenge/attempt，不擅自发会话。命名锁获取结果丢失、释放异常或释放结果不是1时使连接失效，避免潜在持锁连接回池。取消也归还门，应用会话读取不经过此门。

core通过`domain_context`初始化唯一Identity上下文，并把同一上下文交给分派与后台；combined API/后台共用app；standalone API和恢复进程各有自己的门，跨进程同attempt仍由MySQL命名锁排他。这里的1名执行者是每个上下文的资源上限，不是跨机器学校调用总配额。

## 回退与验证边界

运行`deploy/test-query-resources.sh`使用internal网络、无对外端口、随机空库和合成领域响应。登录测试显式通过生产`create_database`创建2+1池，并在容器中启动两个Python进程验证同attempt互斥；不使用默认8连接测试池冒充生产参数。

不把正确终结的别名反向改回running。回滚到缺陷镜像会重新触发多窗口丢传播或登录资源互等，须保留补丁或暂停相关新受理；增加pool_timeout不能解决互等。自动化结果不等于现有部署已升级或真实学校验收，阶段证据见[验收记录](../acceptance/审计修复/R1历史合并与登录资源.md)。
