# 备份恢复与隔离对账

日期：2026-10-03；适用版本：0.15.0。目标机仅需Docker Engine/Compose和系统Shell。生产证书部署/更换不在本轮验收范围。

## 备份

以运维账户创建独立受限目录，不把备份密钥放入应用Secret目录或与备份一起传输：

```sh
mkdir -m 700 /opt/elect/recovery-key /opt/elect/backups
docker compose --env-file deploy/.env -f deploy/compose.yaml -f deploy/compose.ops.yaml run -T --rm --no-deps --user "$(id -u):$(id -g)" -v /opt/elect/recovery-key:/key backup-crypto keygen --key-file /key/backup.key
sh deploy/backup.sh /absolute/deploy/.env elect /opt/elect/recovery-key/backup.key /opt/elect/backups/snapshot.electbackup
sh deploy/backup.sh /absolute/deploy/.env elect /opt/elect/recovery-key/backup.key /opt/elect/backups/logs.binlogbackup mysql_binlogs
```

快照使用MySQL 8.4的single-transaction/source-data=2覆盖七域，同一数据库实例中的逻辑快照包含binlog起点。升级DDL期间暂停备份；禁止复制运行中的MySQL数据目录。封存binlog先轮转，再归档所有已关闭日志；当前仍写入的文件不归档。每日一致性快照及至多15分钟的封存/异机复制频率须在实际运维调度中配置，本轮未部署自动调度或异机目标。

数据经FIFO直接进入分块AES-256-GCM，宿主机不落明文SQL。块序号、头与终止标记均被认证；截断、追加、错误密钥、类型不符拒绝。只有数据库导出与加密两端均成功才原子发布，拒绝覆盖同名输出。加密备份/密钥不进入Git或镜像。

备份覆盖数据库内容及结构版本。所需历史KEK、lookup HMAC、邮箱密钥、会话pepper、服务身份/内部TLS、MQ定义和部署/协议版本通过独立受控渠道保管；不要重新provision已有账户。异机复制后在目标用backup-crypto verify完成完整认证；只保存密钥引用，不将Secret写入公开清单。

## 恢复

先准备新项目的restore.env与受限Secret，保留备份对应的密钥版本，项目名必须为elect-restore-*。恢复脚本拒绝目标已有业务数据或应用/后台正在运行。

```sh
sh deploy/restore.sh /absolute/restore.env elect-restore-incident /absolute/backup.key /absolute/snapshot.electbackup
```

入口总是采用compose.ops.yaml和compose.restore.yaml：学校/SMTP出口断开、五项能力开关强制false、Nginx不发布端口、后台和Relay未自动启动。先完整校验备份，再初始化空库并流式导入；失败保持隔离，不以部分导入为成功。Redis重建，RabbitMQ仅初始化定义；消息和缓存不替代持久状态。

0.15.0的status/backup/restore共用`compose.sh`，按公开env选择standalone/combined及本机覆盖，restore始终最后加载并完全排除host网络SMTP通道。`ELECT_BACKGROUND_ENABLED=false`同时禁止七域API合并任务和独立入口；只读对账也保留此值，不能只停旧Worker。恢复前检查全部profile的运行容器，旧独立Worker不能因被隐藏而绕过停机门禁；组合顺序见[生命周期决策](../decisions/Docker低资源后台生命周期.md)。

恢复门禁撤销旧应用会话、将活动学校凭据置requires_reauth且暂停使用，保留密文/版本；推进监控栅栏并取消旧运行。快照中的待发邮件保留delivery_unknown占名额，未终结支付/上游写保留unknown；即使快照显示prepared/pending，也可能已在快照之后发送。Room/凭据协调旧操作暂停调度；未发布Outbox被隔离到远期，不批量自动重放。门禁可重复执行，行数和历史不删除。

封存binlog已具备加密/完整性验证入口；本轮恢复演练使用逻辑快照。实际时间点恢复应由DBA在同一隔离环境，按快照内SOURCE_LOG_FILE/POS定位后用MySQL 8.4 mysqlbinlog和UTC停止时间回放，再执行recovery-guard apply。没有完成时间点/异机演练前，不声称持续生产RPO达标。

## 对账与恢复执行

- 绑定/删除：按原应用操作、目标与永久发送标记查询本人B02；unknown不重发，缺席按原连续确认策略处理。
- 订单/表单：按原订单回查D02/D04与票据，未验证枚举/空列表不解除未知；D01/E02/E03不重放。用户主动本地取消只结束本系统流程，不退款或保证旧码失效。
- 邮件：按固定Message-ID和SMTP/收件证据核对；无法证明未执行仍占名额，不重发。模拟接受不作为真实收件证据。
- 登录/凭据/默认Saga：核对原协调步骤和学校凭据版本，完成必要补偿/确认后才恢复单账户认证；不清空协调台账来跳过屏障。

先完成逐项对账和密钥校验，再人工批准指定账户/操作的安全继续。通过新的用户认证/业务操作产生新事件；旧Outbox仅逐条核对后恢复，不将available_at整库复位。保持原卷、Secret和日志；升级失败优先向前修复，仅在schema兼容时回退镜像，payment_0004不支持自动降级。

## 可复现演练

```sh
sh deploy/test-stack.sh /absolute/new-dir elect-test-t7
sh deploy/test-t7-recovery.sh /absolute/new-dir elect-test-t7
```

演练在快照后调用模拟D01一次和本机SMTP模拟器接受一封，再恢复旧快照，验证样本/密文可读取且不重发。报告记录真实耗时/行数，保留源和恢复项目的基础服务/命名卷；不是生产异机验收。结束使用同一env/文件/项目down保留卷，普通启停不删除卷。
