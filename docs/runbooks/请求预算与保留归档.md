# 请求预算与保留归档

日期：2026-10-06。0.19.6，R4源码与隔离专项；最新提交CI另见验收记录，现有部署未升级。

## 受理与恢复

同owner的余额刷新和二维码刷新分别每分钟6个新键、滚动24小时60个新键、最多8个非终态映射；手动采集为6/48/8。不同绑定/订单共享额度，合并也计额。数据库owner锁内先重放原键、校验摘要，再检查预算，拒绝事务不留operation/run/映射/Outbox。余额浏览器执行冷却保持30秒。

余额主任务把本次有效绑定集合与错误类别写入`balance_result`，只保存结果判定，不保存学校正文/票据。主任务及首批最多250条先提交，剩余别名由同owner锁内每批250条独立事务续跑；主任务结果立即可读。新请求只合并真实在途主任务，不串成别名链。601条旧映射的分批/重跑已验证。

Payment签名调用方通过`/internal/v1/controls/payment-balance-refresh`提交binding_id/order_id，Room生成原订单固定键，使用独立6/60/8额度。Gateway不能调用该用途，公开DTO拒绝额外来源字段；不增加Secret或服务权限。旧支付固定键保持重放。前端429保存原键和重试截止时间，按钮等待Retry-After，重载后也不自动换键重试。

手动采集新映射保留180天；旧映射的有效保留边界取`MAX(expires_at, created_at+180天)`，后续归档不得按原七天删除。二维码旧映射创建时间安全默认迁移时刻；Room沿用原创建时间。已超新配额的旧数据保留，新键暂停、旧键可恢复。

## 快照回收

每事务最多1000成员、4个父快照，每个owner最多选1个快照，以owner游标轮转。分页共享锁由`FOR UPDATE SKIP LOCKED`跳过，先子后父，原始样本保留；配额仍按父行total计，父行完成回收才释放。

每轮最多10批、开始下一批前检查500毫秒软预算，提交归还连接后让出事件循环。有积压1秒、空闲60秒，业务占用达到基础池大小时15秒再试；原恢复扫描15秒独立计时。SQL本身不承诺500毫秒内完成。停止信号不再开新批，后台关闭不运行清理。

日志只有分类/数量/耗时，逐批记录删除成员/父行、跳过锁数量、候选父行保守成员量、所见最老到期年龄和压力暂停次数；统计最多扫描64个候选，不把候选统计称全库准确积压。

## 升级

最终迁移头为Identity `identity_0004`、Adapter `school_0008`、Room `room_0008`、Monitoring `monitoring_0009`、Payment `payment_0006`、Notification `notification_0003`、Audit `audit_0002`。停止全部旧角色后由统一迁移入口执行再启动，不混跑未计额或不识别冷标识的写者/消费者。QRCode旧创建时间回填迁移时刻，Identity增加会话引用索引；所有领域增加归档目录与冷热去重表，Room增加分批结算摘要。源码清单、schema catalog和[逐表引用清单](../database/保留与归档引用清单.md)由实际迁移声明同步生成。

回退可降低清理频率，字段/索引及180天记录保留；不能删除超额映射、放宽配额掩盖积压，或重新启用旧七天删除规则。

## 临时记录与长期保留

- Identity每60秒最多处理200条终态登录会话引用和200条会话；只有登录尝试过期7天才解联，只有永久失效7天且无剩余恢复引用才删会话。授权同意、登录challenge/摘要防重放记录仍保留。清理不依赖归档成功，不会复活会话。
- Adapter仅擦除到期staged/expired/activated暂存的加密载荷及包裹密钥，每批200行、跳过锁；activated回执与版本、当前学校凭据、预留账号和所有未知学校写保留。
- Room只读操作180天且真实终态、无租约/回查、无实际外键/稳定根引用才转冷。历史主任务有history_syncs引用时继续保留；默认切换/解绑/绑定操作不参与本次物理移除。
- 手动采集与QR映射按创建和终态至少180天保留。手动旧七天记录按`MAX(expires_at,created_at+180天)`检查；QR还要求订单明确终态、无余额pending及后续回查。unknown与取消但学校终态未知的订单均跳过。
- `monitor_attempts`在run/attempt终态180天后归档，运行详情合并冷热attempt并按ID去重。`monitor_runs`保留轻量行作为调度逻辑槽唯一键、样本/手动键/最近运行索引，不假定它们都能删除。
- 原始样本、学校历史、订单、同意、审计、D01/E02/E03发送标记、通知DATA/unknown与其引用默认不物理删除。样本固定分页、前驱链及历史读取维持热表权威。

## 归档形式与去重

采用**本域MySQL内的压缩冷目录**，而不是额外挂载文件目录：`archive_records`保存版本1、行数1、SHA256、压缩载荷及唯一(kind,object_key)。数据库账号/权限不扩大，原密文字段仍是密文；压缩不是加密。离机备份复用既有七库逻辑备份的AES-GCM加密，避免新增卷/Secret与备份原子性缺口。每行上限2MiB，写入后必须读回、解压并验证版本/摘要/行内容一致，才在同事务移除允许移出的热载荷。

批量扫描只收集最多200个标识；传输归档和完整性验证逐行加载载荷，避免一次把200个大JSON/压缩块全部读入128MiB运维进程。单行超过限制时保留热记录并明确失败，不静默截断。

`cold_request_keys`永久保留owner/type/key hash、请求摘要及原结果引用。重放先查热记录，再查冷键并校验归档；无法读取明确503，不能当新请求。Room操作详情支持原ID冷读；监控run和Payment operation继续保留热索引。跨用户404、不同摘要409保持。

`cold_inbox_events`按consumer/event永久唯一。归档先锁热行，写入冷标识后同事务删热行；消费同事务先插热唯一键，再查询冷标识，存在则不执行handler。重复消息可重新留下轻量热标识；它以后到期清理时复核既有冷归档，不覆盖原证据。锁竞争导致的MySQL事务拒绝由原MQ重投，不能把失败事务算业务执行。冷表查询失败不绕过去重。

## 受控维护

使用既有`recovery-guard`一次性容器和运维权限，只连接指定领域；宿主机只需Docker。以下截止时间为示例，归档入口始终再收紧到服务器当前时间减180天。默认dry-run，没有`--apply`不删、不转移。

```sh
sh deploy/compose.sh /absolute/stack.env 项目名 run -T --rm --no-deps \
  --entrypoint python recovery-guard -m services.deployment.retention \
  --domain room --kind room_operations --cutoff 2026-04-01T00:00:00+08:00 --limit 200
```

可选类别：七域的`inbox_events/outbox_events/verify/capacity`；Room的`room_operations`；Monitoring的`monitor_run_requests/monitor_attempts`；Payment的`payment_qr_requests`；Identity/Adapter的`temporary`。状态白名单固定，不能指定任意表或扩大到unknown。旧映射超过配额只暂停新键，不在维护中删除来释放额度。

apply必须先确认具体目标、独立维护窗口、受控摘要与备份，在上例显式加`--apply`。`--batches 1..100`、`--limit 1..200`控制事务范围；SIGTERM只停止下一批，不取消已提交事实。可把受限维护目录挂载到`/maintenance`并指定`--checkpoint /maintenance/r4-room.json`，同domain/kind/cutoff/mode可续跑；dry-run与apply断点不混用。主键游标跨过引用保护行，重跑仍幂等；从头重跑可重新检查上次跳锁行。stdout仅分类/数量，原始归档不导出到日志/Git。

## 备份、恢复与回退

既有`backup.sh`完整导出七库，自动包含归档、冷请求键及冷热Inbox，不需要额外文件同步。`restore.sh`仍使用隔离项目、完整密文认证、空库和禁后台/出口；`recovery_guard apply`增加归档与冷索引一致性校验，损坏时拒绝收口。校验只读目录并按200行推进，之后照常撤销会话、保留unknown并隔离旧Outbox。本版本使用匹配迁移版本的备份/镜像；跨旧版本恢复迁移兼容仍按R7统一验证，不能直接混搭。

冷标识迁移不提供破坏性downgrade。紧急回退优先使用支持本结构的已验证镜像；若必须回退到仅查热表的旧镜像，须先停所有消费者/写者，在维护窗口从已验证归档回填需要的热Inbox、请求映射和operation，保留唯一键并验证旧消息/旧键不执行。没有完成回填与定向验证就不能切回旧代码。

## 容量口径

热载荷转移与压缩不表示全系统磁盘永久有界。归档、冷标识、原始证据与run索引仍随使用增长；这部分不通过删除证据解决。显式`--kind capacity --capacity-limit-mib 1024`可采样当前领域表及索引的MySQL估计字节/行数，`--report /maintenance/capacity-日期.json`排他保存脱敏结果；下一次以`--baseline`引用相同领域报告可输出字节/日增长率。预算由部署者按目标磁盘分配，示例1024MiB不是生产承诺。达到该预算输出over_budget=1并退出2，供现有运维告警接入。

容量估计不含MySQL日志、备份及其他卷；目标机同时监测磁盘使用率，建议80%预警、90%停止非必要新查询并安排扩容/受控归档，不自动删除原始证据。长期增长率、目标机2核2GB/50人24小时仍待实际验收。
