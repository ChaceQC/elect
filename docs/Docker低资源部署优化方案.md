# Docker 低资源部署优化方案

日期：2026-10-04（Asia/Shanghai）。审查代码版本：0.13.2；历史运行样本版本：0.13.1；第一批实现版本：0.14.0；第二批：0.15.0；第三批：0.16.0；第四批：0.17.0；第五步镜像批：0.18.0。

状态：前四步已交付，13容器共享生命周期、2+1连接池、基础参数及提交后Outbox提示/推送/双槽执行已通过隔离回归；第五步镜像发布/分阶段启动实施，页面请求/留存与2核2GB/50人24小时容量未验收，原业务部署保持停止。实施与验证见[生命周期决策](decisions/Docker低资源后台生命周期.md)、[资源参数决策](decisions/Docker低资源资源参数.md)、[第三步验收](acceptance/Docker低资源第三步验收.md)和[第四步验收](acceptance/Docker低资源第四步验收.md)。

## 1. 目标与结论

用户指定按 50 人计算，目标机器只安装 Docker Engine/Compose。容量方案覆盖 50 名用户均开启持续监控，并分别验证日常页面访问和 50 人操作突发；50 名用户不等于持续 50 请求/秒。

原独立架构的历史容器内存实测约2.74GiB，其中26个Python业务进程合计约2.01GiB。0.15.0完成同域合并，本轮同一隔离项目启动后单次CLI快照为30容器2623.91MiB、13容器1376.16MiB；未加载OCR、未覆盖负载/备份峰值或宿主机开销，不能直接认为满足2核2GB。0.16.0在另一新空库项目首次健康时实测1237.68MiB，冷启动2秒采样峰值1257.93MiB、各容器零OOM；与本轮旧版本1394.09MiB末次快照约降11.2%。OCR另在无网络容器测量。短窗口仍未覆盖宿主机/50人/备份峰值，后续按第五至六步推进，最终结论以目标机器验收为准。

监控间隔为 60–1440 分钟。按最短间隔和每用户一个监控计算，50 人每小时约产生 50 次计划采集，每日约 1200 次；手动查询、历史同步、认证恢复、重试及邮件另计。启动恢复和同时到期会形成突发，不能只按平均值配置执行能力。

本方案保留现有功能和可靠性语义，不以删除恢复器、取消持久台账或提高学校限流上限换取资源下降。学校绑定、真实 SMTP、支付及真实验收范围沿用原开关与授权，不因容量目标而扩大。真实 D02 终态、生产异机/PITR 和 T8 发布的未完成状态不变。

## 3. 建议的进程与容器组成

同一领域内将 API、Relay、恢复和调度角色合并到一个 Python 进程，复用本域运行上下文、数据库连接池和 HTTP 客户端。Gateway 继续无数据库；不同领域仍通过现有认证接口和可靠事件协作。邮件发送保留独立进程和出口。

| 领域或组件 | 当前进程/容器数 | 建议数 | 合并范围 |
| --- | --- | --- | --- |
| Gateway | 1 | 1 | 保持无业务库 |
| Identity | 3 | 1 | API、Relay、恢复 |
| School Adapter | 3 | 1 | API、Relay、凭据清理；保留唯一学校出口 |
| Room | 3 | 1 | API、Relay、同步/默认/绑定/查询任务 |
| Monitoring | 6 | 1 | API、Relay、Scheduler、Worker、恢复、提醒结果处理 |
| Notification | 4 | 2 | API/Relay/恢复合并；发送 Worker 独立 |
| Payment | 4 | 1 | API、Relay、Worker、恢复；支付能力仍受原开关控制 |
| Audit | 2 | 1 | API、消息消费 |
| Nginx、MySQL、Redis、RabbitMQ | 4 | 4 | 保留基础服务 |
| **合计** | **30** | **13** | Python 业务进程由 26 个降至 9 个 |

目标机器确需当前 TUN 环境的 SMTP 定向通道时，再增加 1 个容器，并将其资源计入预算。是否需要该通道以目标机网络为准，不能直接照搬本机物理网卡配置。

进程合并扩大了同域角色的共同故障范围。需要统一监督后台任务、独立健康状态和完整退出流程；仅用 Supervisor 在同一容器运行多个 Python 进程，不能取得上述常驻内存收益。

## 4. 优化事项

优先级P0为保证合并正确性的前置工作，前三批已完成Monitoring试点、七域推广/恢复适配及资源参数；P1剩余执行效率、P2持续运行和交互优化，继续按第6节第五至六步推进。

### 1. P0：同域角色共用运行上下文

- 将角色入口整理为可由统一生命周期管理的异步任务，共用一个本域数据库 engine 和可复用的 ServiceClient。
- 保留独立角色入口供现有部署和故障测试使用；轻量模式启动合并角色时，原独立 Worker/Relay 必须禁用，避免重复启动。
- 同域共享 AMQP 连接时，为发布和不同消费者保留合适的独立 channel、confirm 和 QoS 配置。
- 保留七域独立数据库、最小权限账号、Secret、消息签名及内部 TLS；不跨域 SELECT 或合并高权限账号。

主要落点：[服务工厂](../backend/services/common/app.py)、[业务初始化](../backend/services/common/business.py)、各域 job/process 入口及 Compose。

### 2. P0：任务监督、独立心跳和退出

- 审查基线的Heartbeat固定写入`/tmp/elect-job-health.json`；0.14.0已改为[角色独立心跳](../backend/services/common/heartbeat.py)，Monitoring合并模式汇总为容器健康。
- 单一入口负责信号、停止领取新任务、等待或取消在途任务、释放连接；不得直接并行调用多个各自注册信号的现有 `run()`。
- 任一必需角色停止推进时，健康状态应反映故障；不能因 API 可响应而掩盖 Scheduler 或 Relay 已退出。
- 按最长必要任务预算设置退出宽限，保留采集续租、支付发送标记、SMTP DATA 边界及未知结果恢复，避免统一缩短为 30 秒。

### 3. P0：恢复隔离适配合并角色

- [恢复编排](../deploy/compose.restore.yaml)目前通过独立 Worker/Relay 的 profile 控制后台运行；合并后新增明确的后台禁用模式，恢复时 API 进程也不得自动启动后台角色。
- 保留无外部出口、空库检查、停止业务进程和旧 Outbox 隔离；只读对账场景按明确角色启动。
- 同步 [restore](../deploy/restore.sh)、[集成入口](../deploy/test-stack.sh)和恢复验收。原测试按服务名停启独立 Worker，必须适配新角色组合。
- 验证两种模式不能同时领取同一组任务；即使误启动或进程重启，租约、幂等和代次屏障仍须生效。

### 4. P1：Outbox 按需唤醒与空闲退避

六个 Relay 正常连接且空闲时各约每秒扫描一次，仅此项理论上每日约 51.8 万次扫描。0.17.0已实现事务成功提交后唤醒本域 Relay，空闲采用 `1 → 2 → 5 → 10 秒`退避，有积压每批最多16条。进程内唤醒仅用于降低延迟，可靠性继续依靠数据库扫描，不能在事务提交前把事件视为可发布。

保留 [Outbox](../backend/services/common/outbox.py)发布租约、confirm 后更新、失败重试和去重语义；故障退避加入抖动，避免依赖恢复时所有角色同时重连。

### 5. P1：按任务性质设置扫描周期

[学校凭据清理](../backend/services/common/business_worker.py)0.17.0由每秒UPDATE改为每60秒、最多100行一批；积压继续小批，沿用state/expires_at索引顺序，每10秒实际读库保持健康。认证有效性仍在使用凭据时校验，不能依赖清理任务是否已运行。

调度扫描、租约续期、取消屏障和恢复分别设置周期；不将全部任务统一调慢。保留用户监控间隔和原调度锚点，同一时刻到期的任务通过有限执行并发消化。有大量积压时限制单次事务批量，及时释放数据库锁。

### 6. P1：消息推送消费

审查基线的多个消费者使用 `queue.get()`，其 timeout 是请求等待预算，不等于等待新消息的长轮询。0.17.0已改为basic.consume回调、有界prefetch=1/本地缓冲、独立channel与重连失效处理；方法get只取本地消息。

保留消息签名、Inbox 去重、提交后 ACK 和发布确认；MQ 不可用时，已有持久任务继续通过低频数据库扫描恢复，不以队列是否有消息判断是否存在任务。

### 7. P1：重新计算数据库连接池

0.16.0将combined的[连接池](../backend/services/common/database.py)固定为`pool_size=2`、`max_overflow=1`，8池理论24条应用连接（原40条）；Gateway仍无库。3秒等待/超时/归还、50次控制读取和学校等待期间真实续租均通过；standalone保留2+3。

combined的MySQL `max_connections=40`留16条给迁移、备份和运维，本轮最高19条/零上限错误。后台学校等待不占事务，池不能无限等待；后续持续负载仍须记录连接等待。

### 8. P1：MySQL 小内存参数

standalone的[MySQL配置](../deploy/mysql/conf.d/elect.cnf)为200连接、512MiB Buffer Pool；combined的[附加配置](../deploy/mysql/low-resource.cnf)采用下表参数。MySQL限额640MiB，首次空库内核峰值429.73MiB，Buffer Pool不等于总占用；完整数据量与备份峰值留待目标机验收：

| 参数 | combined实际值 |
| --- | --- |
| `innodb_buffer_pool_size` | 128MiB |
| `max_connections` | 40，依赖上一项连接池改造 |
| `table_open_cache` | 256 |
| `table_definition_cache` | 400 |
| `temptable_max_ram` | 32MiB |
| `tmp_table_size`、`max_heap_table_size` | 各8MiB |

Buffer Pool 不等于 MySQL 总内存。容器限额还须容纳连接、内部结构、临时表、冷启动和备份客户端。保留事务持久性、binlog 和现有备份要求；依据查询计划与慢查询调整索引，不以关闭审计、持久写入或恢复能力作为默认优化。

### 9. P1：RabbitMQ 管理组件和线程

0.16.0的combined使用固定摘要普通4.1.4-alpine镜像、128MiB绝对水位/256MiB容器限额及1调度/2异步/各1脏线程；standalone保留management。[状态脚本](../deploy/status.sh)继续通过CLI查询，未发布管理面。实际流控、解除后Outbox投递与重复签名事件通过。

[Secret生成器](../backend/services/deployment/provision.py)已改为4.1核心`definitions.import_backend/local.path`；combined另选公开配置兼容旧`management.load_definitions` Secret文件，复用账号、权限与队列。新空库和原卷13→30→13升级通过，持久消息、confirm、手动ACK和未知台账保留。

### 10. P1：Redis 内存与持久化预算

standalone保留[Redis配置](../deploy/redis.conf)128MiB数据/256MiB容器；combined采用32MiB数据/96MiB容器。独立无网络实例写满、AOF重写并发、重启全部通过，内核峰值72.27MiB、零OOM和零淘汰。

保留 ACL、TTL、AOF 和 `noeviction`；认证状态、每账号锁和全局并发槽不能因内存不足被自动淘汰，Redis 故障也不能退回各进程独立字典。内存水位、写入失败和认证恢复需纳入状态检查。

### 11. P1：健康探针降频并区分角色健康

原26个Python容器每10秒探针理论156次/分钟，0.15.0为54次；0.16.0的9个进程改30秒后理论18次/分钟，基础服务同样30秒。启动期5秒探测，API/Redis/Nginx两次失败，MySQL/RabbitMQ四次；后台真实心跳与20/45秒失效窗口保留。

后台真实进度心跳继续独立更新；调整扫描间隔时同时核对现有 20 秒健康判定。依赖探测可短时复用结果，完整保留数据库/迁移版本检查和 degraded 状态，不能用固定成功响应取代就绪检查。

### 12. P1：OCR 线程、冷加载和镜像依赖

当前已实现 [模型延迟加载](../backend/services/school_adapter/infrastructure/ocr.py)及 [单次推理锁](../backend/services/school_adapter/application/sessions.py)，继续保留。0.16.0锁定已有ddddocr 1.6.1/ONNX Runtime 1.30，受限会话采用计算/跨算子各1线程、顺序执行与关闭自旋，BLAS/OMP各1。匹配1CPU的无网络合成图对照结果摘要相同，线程17→2、推理P50 82.06→12.76ms、2秒空闲CPU 0.3045→0秒；这是单图样本，不是学校识别率/多账号容量验收。

可将 OCR 重依赖拆到 Adapter 镜像，主要改善构建、拉取与镜像磁盘开销；普通服务安装了 OCR 包不代表已加载模型。人工登录仍由用户回答验证码，不能为节省资源改变认证流程。

### 13. P1：预构建镜像与分阶段启动

0.18.0的[CI](../.github/workflows/check.yaml)在版本标签触发时，完成全部容器验证后直接发布本次集成受测的前后端runtime镜像，不重新构建；生成版本/源提交/全部摘要清单及仅deploy的开发版资产。[启动入口](../deploy/start.sh)要求published模式/固定摘要、校验镜像标签并在停旧角色前预检入口；随后基础服务→迁移→领域服务→后台→Nginx依次就绪，显式--parallel 1/--no-build/--no-deps。开发构建移至compose.build.yaml，目标包无需前后端源码。详见[运行手册](runbooks/固定镜像发布与启动.md)，实际发布结果见[镜像验收](acceptance/Docker低资源第五步镜像验收.md)。

2GB 主机不承担 Node 构建、浏览器测试和完整并行集成环境。基础服务、迁移和应用按依赖分阶段启动，并限制启动并行度，覆盖新空库及已有卷升级两条路径。构建和运行各自的 Dockerfile 多阶段隔离、锁文件和 Secret 排除继续保留。

0.16.0为两段uv sync增加BuildKit共享锁定依赖缓存，仍使用--locked，避免仅版本元数据变更再次下载全部OCR依赖；本机从旧测试镜像中的相同锁定依赖播种缓存后正式Dockerfile构建通过，生产镜像不包含缓存。固定镜像发布流程由0.18.0接通，目标机容量仍待第六步。

0.15.0已提供专用`compose.low-resource.yaml`和统一`compose.sh`选择入口，状态/备份/恢复/升级使用同一配置组合；已有卷切换先停止全部旧角色，详见生命周期决策。固定镜像发布实施见0.18.0镜像验收；目标机容量尚未交付，不能将轻量入口视为2GB可用声明。

### 14. P1：有限业务并发与排队

0.17.0已实现2个监控异步执行槽、邮件发送保持1个槽，并通过3合成账号排队/两槽续租/取消/关闭及无MQ回归；Uvicorn 保持单进程，避免为每个后台角色再复制解释器。根据真实执行延迟调整，学校全局最多 5、后台最多 4、每账号最多 1 的共享限制继续生效，并保留交互通道。

学校超时、429 和依赖故障进入原有持久退避，不能通过增加 Worker 绕过限流。记录 50 个同时到期任务的最老等待时间和消化时间，避免排队无限增长或在恢复后补跑过期的所有历史槽。

### 15. P2：页面请求与校园共享出口

[监控页面](../frontend/src/features/monitoring/MonitorPage.jsx)当前每 15 秒读取状态，50 人同时停留时仅此查询约为 3.3 次/秒。稳定状态可评估 30–60 秒刷新，操作后立即失效刷新；保留现有异步操作的渐进轮询、终态停止和隐藏页面暂停行为。

[Nginx 登录限流](../deploy/nginx/default.conf.template)为每 IP `10r/m`、`burst=5`。验收应覆盖 50 人共享校园出口的情况，结合 IP、账号及验证码挑战维度校准；不能直接取消认证防护。已有静态资源长缓存与 API `no-store`继续保留，不缓存用户私有响应。

### 16. P2：数据留存、日志与运维峰值

50 人每小时采集，按 365 天约产生 43.8 万条样本；尝试、Outbox/Inbox、审计与历史同步另计。按 [既有保留政策](后端实施计划.md)规划样本 12 个月、详细尝试 90 天、操作/幂等台账至少 180 天的小批清理；实际策略需覆盖引用关系、消息重投和备份恢复窗口。未知写入与未解决订单不进入普通清理。

保留现有日志轮转和脱敏，按磁盘日增量评估保留期。备份沿用流式加密，把备份容器与 MySQL 客户端的额外开销计入高峰；同机不并行启动第二套完整测试/恢复栈。使用现有状态入口补充内存峰值、CPU 限流、连接等待、队列积压和磁盘指标。

## 5. 运行内存预算

下表为改造后的占用目标，不是已经测得的结果，也不是可直接照抄的 `mem_limit`。

| 部分 | 建议运行占用目标 |
| --- | --- |
| 9 个 Python 进程，含已加载 OCR | 约 850MiB |
| MySQL | 约 350MiB |
| RabbitMQ | 约 120MiB |
| Redis | 约 32MiB |
| Nginx | 约 16MiB |
| **应用容器合计** | **约 1368MiB，约 1.34GiB** |
| 操作系统与 Docker | 预留约 350–450MiB |

可选 smtp-direct、备份作业、探针、页缓存和冷启动波动需另外计入峰值。验收记录实际 `MemTotal`，不能把厂商标注的 2GB 自动当成可分配给容器的 2048MiB。容器限额应依据各组件峰值和全机可用内存配置；单项限额之和不构成全机资源保证。

CPU 预算以整套应用共享 2 vCPU 验证，避免给关键数据库或续租任务设置过紧配额导致长期节流。Swap 可作为应急措施评估，但不能把持续交换当作 2GB 容量达标。

## 7. 验收条件

使用专用的 2 vCPU、2GB 虚拟机或等效全栈资源边界；若采用 cgroup，必须计入整套服务并另外核算宿主机开销。不能在 16GB 主机上分别给每个容器 2GB 上限，然后声称整套系统通过 2GB 验收。压测发起端放在独立机器。

| 场景 | 必须验证的结果 |
| --- | --- |
| 空库、首次初始化与已有卷升级 | Secret/权限/迁移/就绪顺序正常，无 OOM，记录峰值 |
| 50 人监控，连续至少 24 小时 | 按 60 分钟间隔运行，统计实际到期/完成/失败/重试，不漏持久任务、不重复提交样本，积压不持续增长 |
| 50 人页面访问和操作突发 | 分别记录页面读取、登录、手动采集的延迟、错误、限流与队列等待，覆盖同一 NAT 出口 |
| 50 个同时到期任务 | 模拟学校正常、秒级延迟和慢响应，记录消化时间及交互请求表现；不只使用原脚本的 30ms 响应 |
| OCR 与认证恢复 | 冷加载、已加载模型、多个账号同时恢复时内存受控，学校并发和人工验证码规则不变 |
| MySQL/Redis/MQ 故障及进程重启 | 保留持久任务，消息重投无重复结果，失效执行不能绕过租约或代次屏障 |
| 取消、关闭、默认切换与授权撤回 | 合并角色不改变原控制语义，迟到执行不能继续提交或取得新发送许可 |
| SMTP/支付不确定结果 | 在合成故障中保持一次发送边界、有限重试与 unknown 台账，不能自动重发未知写入 |
| 备份并发及恢复隔离 | 备份额外资源在预算内，恢复时所有后台角色和出口均受控，旧 Outbox 不自动重放 |
| 长期资源 | 记录全机可用内存、容器/cgroup 内存峰值、OOM、Swap I/O、CPU 节流、数据库连接、队列与磁盘增长 |

建议以全程无 OOM、无持续 Swap 抖动、稳态全机可用内存至少 200MiB、无持续增长积压作为资源通过条件；同时记录最差峰值和冷启动/备份窗口，不能只展示稳态平均值。未满足时继续调整，不能仅下调容器硬限额后标记通过。

本地容量使用模拟学校和模拟邮件/支付服务；真实学校支持人数、限流和最终支付/邮件结果需在既有指定验收范围内另行记录。当前 [T7 容量脚本](../backend/scripts/t7_capacity.py)是单进程并发、30ms 模拟学校的单轮测试，其吞吐不能替代本节验收。
