## SEC-01：支付传输允许 HTTP 和协议降级（已忽略）

**处理结论：** 用户明确“忽略，无法解决”，本项从整改清单移除，不再作为本次审计要求修改支付链路的门槛。以下保留原始协议与复现事实，不表示已修复，也不自动改变既有支付开放和验收规则。

**位置：** [payment_protocol.py](../../backend/services/school_adapter/infrastructure/payment_protocol.py) 第 18–39、107–132 行；[payment_transport.py](../../backend/services/school_adapter/infrastructure/payment_transport.py) 第 36–75 行；[payment_flow.py](../../backend/services/school_adapter/application/payment_flow.py) 第 55–101 行。

`check_pay_url()` 显式允许 `cwcwx.hbue.edu.cn` 的 HTTP 地址。`PaymentTransport` 逐跳仅保持主机相同，没有保持 HTTPS；因此 HTTPS 地址返回到同主机 HTTP 的重定向也会被接受。返回图片仅检查格式、尺寸和可解码性，没有能够验证收款对象/订单绑定的可信签名。

**影响：** 学校返回 HTTP 支付地址时，或 HTTPS 支付页返回降级跳转时，能操纵这段链路的攻击者可替换二维码图片、表单状态和原支付页文案。用户看到的是本应用同源返回的图片，浏览器入口 HTTPS 无法补足后端到学校的传输完整性。可造成错误收款码展示；不据此断言已发生资金损失。支付确认的同金额候选兜底还读取该原支付页，但仍要求独立 D04 候选，不能称为单靠文案即可任意伪造已支付。

**复现：** 对原 `PaymentTransport.request()` 注入无网络 MockTransport：初始 HTTPS 请求返回同主机 HTTP 重定向，随后返回合成 PNG。实际请求协议序列为 `https → http`，原 `image_bytes()` 接受该 PNG。

**现存约束：** 公开模板默认关闭支付；本问题不要求关闭 TLS 证书校验，也不是任意主机 SSRF。学校 API 文档已经记录该 HTTP 协议，本项属于兼容既有上游时保留下来的安全风险，不能无依据把 URL 改为 HTTPS 后宣称真实支付可用。

**当前动作：** 不修改协议，不限制或替换现有支付入口，不安排本项修复。

## SEC-02：匿名验证码限流可以轮换浏览器标识绕过（已忽略）

**处理结论：** 用户明确要求忽略，本轮不调整该实现。以下为原始观察和建议，不列入当前整改。

**位置：** [gateway/api.py](../../backend/services/gateway/api.py) 第 58–72 行；[redis_store.py](../../backend/services/school_adapter/infrastructure/redis_store.py) 第 69–78、140–147 行；[default.conf.template](../../deploy/nginx/default.conf.template) 第 34–55 行及 [local.conf.template](../../deploy/nginx/local.conf.template) 第 26–47 行。

验证码接口不要求应用会话。Gateway 在没有合法长度 Cookie 时直接生成新匿名标识；已有 Cookie 也只检查长度。Adapter 的取图限流键只有该标识的哈希。Nginx 的 IP 限流仅配置在精确 `/api/v1/auth/login`，验证码路径落入无此限制的 `/api/`。

**影响：** 同一来源可以不保留 Cookie或反复更换 43 字符 Cookie，为每个请求获得独立次数额度。每次调用都会启动学校登录页/验证码请求及缓存写入。学校侧 5 个全局并发槽限制同时进行的请求数量，不能限制等待请求数量、总请求速率或 Redis 标识数量；匿名流量可以挤占正常登录及共享学校请求资源，造成拒绝服务。

**复现：** 在原 `_create_challenge()` 上，同一 nonce 的第 6 次调用返回 429；6 个不同 nonce 则全部进入模拟学校 `challenge()`。模型在同一时间窗内执行，没有操作真实 Redis 或发送学校请求。公开代理缺少验证码 IP 限流由两份模板直接确认。

**整改：** 在两种 Nginx 入口为验证码及其他匿名认证入口增加一致的来源速率/并发预算，并在服务端设置取图的总体受理上限。浏览器 nonce 只作为验证码归属信息，不承担唯一的反滥用身份。超过预算应在请求学校前返回 429，并验证轮换/丢弃 Cookie 不能绕过。

## SEC-03：首页采集查询形成无上限的持久写入放大（0.19.1源码已修复）

**修复结果：** 本人monitor锁内按有序成员摘要复用；新建最多6次/分钟、保留12快照/60,000成员、单集合20,000条，超限429且不截断。token以用途隔离HMAC重建，数据库只存hash；旧token保留到原TTL。recovery每60秒清理最多4快照/1,000成员，分页共享锁防止清理竞态，先子后父且不删除原始样本。详见[实施规则](../decisions/查询资源受理与快照清理.md)。以下为0.19.0原始问题解释和证据。

**通俗解释：** 为了让用户从第一页翻到第二页时，列表不被新采集的数据挤动，后台会先保存一份“这次查询有哪些记录、按什么顺序排列”的清单。这份清单就是快照，保存的是记录 ID 和序号。

例如，所选日期范围有 1,000 条采集记录，页面每页显示 10 条：

| 操作 | 页面取得的数据 | 数据库额外保存的快照成员 |
| --- | --- | --- |
| 第一次查询第一页 | 10 条 | 1,000 条 |
| 使用同一快照翻到第二页 | 10 条 | 不再新建快照 |
| 重新查询第一页 | 10 条 | 再增加 1,000 条 |
| 同一范围累计重新查询 10 次，假设样本数量不变 | 每次显示 10 条 | 累计 10,000 条 |

**问题在于旧清单会不断累积。** 30 分钟后快照不能再用于翻页，但数据库没有自动删除这份清单的逻辑；第一页可见时每 60 秒的自动刷新也会创建新清单。所以普通长期使用会逐渐增加磁盘占用，频繁请求则会加快写入和 I/O 消耗。原始采集记录本身没有因此重复采集，余额等完整数据也没有被整份复制。

整改目标是保留翻页稳定性，同时让这些临时清单可以安全复用、限制数量并在到期后清理；该目标已由0.19.1实现，原始复现数据不作为新版本行为。

**位置：** [gateway/query_api.py](../../backend/services/gateway/query_api.py) 第 98–128 行；[monitoring/samples.py](../../backend/services/monitoring/samples.py) 第 50–105、109–132 行；[初始迁移](../../backend/services/monitoring/migrations/versions/0001_initial.py) 第 361–411 行。

没有 `snapshot_token` 的首页请求总会新建一条 `sample_snapshots`，随后将整个所选日期范围的全部样本 ID 和序号写入 `sample_snapshot_items`。`page_size <= 100` 仅限制返回查询，不能限制前面的成员写入；同一用户/绑定/范围也没有有效快照数量、频率或成员总数配额。

快照到期只影响 token 可用性。全量检索未发现删除过期快照及成员的运行入口，外键是 `RESTRICT`，也不会因到期自动删除。前端首页定期获取新快照使普通使用也会重复产生成员记录。

**影响：** 一个有本人绑定的用户反复请求首页，就能以每次 N 个匹配样本的规模写入 N 条成员，R 次请求形成 R×N 条成员记录。消耗共享 MySQL 的磁盘、事务日志、连接和 I/O；过期后仍保留。无需学校写、支付或邮件权限，也不涉及读取别人的样本。

**复现：** 调用原 `snapshot()`，仅将 SQL 执行替换为 SQLite 内存库，并适配 MySQL 的 30 分钟时间函数。3 条合成样本、`page_size=1`、同一范围连续 2 次请求，得到 2 个快照和 6 条成员。该结果证明写入语义，不是 MySQL 并发、磁盘容量或耗尽速度实测。

**整改：** 在保持分页成员固定的前提下增加每用户创建速率、有效快照数量/成员总额限制及可安全复用的快照策略；实现有界、可观测的过期成员与快照清理，处理成员外键顺序。验证重复首页请求、多个标签页、token 过期和迟到样本不会破坏分页一致性。

## SEC-04：无效验证码先消耗目标账号额度（正常行为，已忽略）

**处理结论：** 用户确认“是正常的，忽略”。无效验证码计入账号额度属于预期规则，本项撤出安全问题与整改清单；保留当前限流顺序和次数。以下为原始行为观察和复现记录。

**位置：** [authentication.py](../../backend/services/school_adapter/application/authentication.py) 第 31–45 行；[login.py](../../backend/services/identity/application/login.py) 第 24–71、203–214 行；[redis_store.py](../../backend/services/school_adapter/infrastructure/redis_store.py) 第 69–78、162–174 行。

认证处理先根据用户提交的 `student_id` 计算账号别名，扣减该账号每分钟 5 次的额度，然后才检查并消费 challenge。Identity 在此之前只校验请求格式、协议版本和本地尝试的一致性，没有证明 challenge 真实存在或属于当前浏览器。

**行为：** 格式有效但不存在的 challenge 仍计入提交学号的认证预算；账号预算耗尽后返回 429。用户确认接受这一规则，不再将此行为单独列为安全缺陷。

**复现：** 原 `_authenticate()` 对同一合成学号收到 5 个不存在的 challenge，均返回 `400 CAPTCHA_EXPIRED`；第 6 次在 challenge 校验前返回 `429 RATE_LIMITED`。学校认证函数没有执行。

**当前动作：** 不调整 challenge 校验与账号扣减顺序；SEC-02亦已按用户要求忽略。

## SEC-05：历史同步可以持续堆积不同范围的待办（0.19.1源码已修复）

**修复结果：** 本人偏好锁内先查幂等重放，再检查新operation上限（6/分钟、24/24小时、8个非终态，合并别名也计入）及2个未完成sync/64个未完成窗口上限；所有检查先于新持久写入。被当前同绑定范围完整覆盖则合并；部分重叠仍在配额内独立受理，缓存不阻止显式刷新。超限429且不留下operation、sync、窗口或Outbox；原幂等保留与租约语义保持。以下为0.19.0原始调用链证据。

**位置：** [gateway/query_api.py](../../backend/services/gateway/query_api.py) 第 81–95 行；[query_jobs.py](../../backend/services/room/query_jobs.py) 第 29–60 行；[history_jobs.py](../../backend/services/room/history_jobs.py) 第 16–84、88–125 行；[dates.py](../../backend/services/common/dates.py) 第 16–34 行。

`accept_query()` 对每个新幂等键先创建持久 operation。`accept_history()` 仅合并“绑定、起止日期完全相同且仍在运行”的同步；换一个日期范围就会创建新 sync，并按每 7 天一个窗口插入任务，单次 366 天请求可创建 53 个窗口。没有每用户待办数量、累计待同步天数、请求速率或全局队列受理上限。同范围合并虽然避免重抓，也仍会留下新的 operation。

**影响：** 有效用户可提交许多不同、重叠范围使数据库和学校查询队列持续增长。调度器的每账号单个运行窗口只限制执行并发，并不限制入队数量；绑定/支付/邮件副作用开关不会关闭此只读学校查询能力。可拖慢正常历史同步并持续消耗学校访问预算。

**证据：** 静态追踪入口→受理→窗口生成→调度，确认整条受理链未检查上述配额；未运行学校负载或实际任务堆积实验。

**整改：** 在用户锁内检查待办数量与累计窗口预算后再写入，合并重叠窗口并考虑已成功缓存范围；为重复合并请求设置有界的幂等映射/保留策略。使用明确的 429/409 和已有操作引用反馈，验证并发受理不能穿透限额。

## 现存部署风险与加固建议

1. **私网 HTTP 仍然明文传输登录密码与会话。** `gateway/cookies.py` 根据 HTTP 模式取消 Secure，登录表单直接提交密码；这符合此前用户指定部署方式，但私网地址本身不提供防窃听能力。应把它视为明确的网络信任假设，正式推广采用 HTTPS 或已验证的加密访问通道。本轮未检查或修改现有部署，也不把此前被批准的 HTTP 兼容当成本轮新增回归。
2. **standalone/combined 的部分内部 HTTP 是信任边界。** `common/service_client.py` 第 15–17 行及 `deploy/compose.yaml` 的 Nginx→Gateway 仍有 HTTP；签名 JWT 不能保护请求/响应正文的传输机密性和完整性，且 `jti` 仅格式校验、不提供一次性防重放。该风险需要内部网络控制能力，不能当作公网匿名越权；core 的 Nginx/外部 Worker→core 使用内部 TLS，进程内调用仍验证身份，但同进程持有多个域 Secret 扩大了单点失陷范围。
3. **CI 应收紧写权限和持久凭据。** `.github/workflows/check.yaml` 第 12、16 行使整个 check 作业持有 `contents: write, packages: write`，checkout 未关闭 `persist-credentials`。建议验证作业仅保留读权限，标签发布放到独立作业并在验证成功后授予写权限，第三方 Actions 固定提交。fork PR 默认令牌权限会被 GitHub 降为只读，本轮没有验证仓库例外设置，不能宣称所有外部 PR 都持有写令牌。
4. **Nginx 缺少统一浏览器安全响应头。** 两份模板没有 CSP、`frame-ancestors`/X-Frame-Options、Referrer-Policy 或默认 HTTPS 的 HSTS。作为纵深防护补齐，并适配 QR blob 图片与图表；没有仅据头部缺失报告可利用 XSS，跨站 iframe 会话还受到 SameSite=Lax 的限制。
5. **依赖扫描与镜像系统包更新需要持续门禁。** CI 当前执行功能与容器验证，未见依赖漏洞/SBOM 检查。固定镜像摘要保证来源一致，不代表系统包永远没有漏洞；本轮没有拉取/扫描所有镜像的 OS 包，也没有扫描历史镜像或历史 Git 对象。

## 已核对的安全控制

- 公开业务入口从 Cookie introspection 获取用户，写接口校验 Origin 和会话 CSRF；对象查询以 owner 条件或 `authorize_owner` 限定本人。
- 内部 JWT 固定 EdDSA，校验可信 key、issuer、audience、scope、60 秒 TTL 与用户上下文格式；core 直接分派保留原身份依赖和 DTO 校验。
- 账号密码、学校 token、支付会话及邮箱采用带对象 AAD 的 AES-GCM；生成器使用系统随机数，未在运行容器挂载内部 CA 私钥。
- 学校正常认证/读取逐跳限制 HTTPS 主机、端口和目标 IP，DNS 解析结果固定到实际连接；未发现来自公开请求的任意 URL 目标。
- 支付金额由后端限定 1–500 元整数，学校目标由本人绑定取得；D01/E02/E03 的 dispatched 台账阻止未知结果自动重发；二维码接口再次检查本人订单。
- 邮件正文采用纯文本、收件地址过滤 CR/LF 等字符，SMTP 强制正式 TLS，发送前有持久许可及 DATA 边界记录；正文后断连保留 unknown。
- SQL 查询值使用绑定参数。Bandit 对 Room 查询、Outbox 和恢复表名的拼接命中经人工检查为固定片段或严格表名约束，不认定为公开 SQL 注入。
- Secret/真实 auth 文件受到 Git 和构建上下文排除；生产前后端镜像不携带测试环境，备份分块认证，恢复先验证完整备份、要求隔离空库并禁止后台/外发。
