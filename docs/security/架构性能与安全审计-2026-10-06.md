## 2. 总体判断与证据口径

当前代码已形成 Gateway、Identity、Room、Monitoring、Payment、Notification、School Adapter 与 Audit 的职责分工。`core` 模式将部分领域放在同一个进程，但仍保留领域数据库、账号、连接池和内部权限检查；Adapter 与邮件发送 Worker 独立。现有微服务领域划分是设计前提，本报告不建议无依据推翻它。

主要短板集中在这些边界的组合：

1. **受理与执行没有统一预算。** 部分接口去重了学校执行，却仍持续插入请求映射；有些清理入口的吞吐与可积压规模不匹配。
2. **状态关联与执行阶段混用。** 历史合并请求依靠会被覆盖的 `saga_step` 传播状态，形成无法自动释放的待办。
3. **局部资源限制不等于完整调用链有界。** 登录长期占用池内连接后又申请同池连接；历史执行预算没有与租约统一；OCR 协程取消不终止底层线程。
4. **并发结果缺少一致的时间顺序。** 余额的不同写入入口对新旧结果采用不同规则。
5. **故障检测与恢复未闭环。** 角色退出后没有自动恢复路径；持续失败可能仍通过合并模式健康检查；进程内分派丢失部分领域错误信息。

证据等级：

| 标记 | 含义 | 不能据此声称 |
| --- | --- | --- |
| 静态确认 | 已核对实际调用、SQL 条件或配置，能明确说明触发条件 | 已在生产触发或已测得损失 |
| 内存复现 | 提取基线中的原函数，在无网络、无持久文件的模型中观察结果 | 真实 MySQL 调度、真实 OCR 峰值或学校联调通过 |
| 条件性风险 | 缺少保护的路径已确认，实际影响需要并发、延迟、故障或长期数据量条件 | 所有正常请求必然失败 |
| 容量推算 | 按代码上限、批量及周期计算 | 压测吞吐、实际积压或实测恢复耗时 |

优先级是整改建议，不是 CVSS 分数或已发生事故等级：P1 优先修复会阻断实际流程的缺陷；P2 按影响和工作量安排。全部发现当前均为**未整改**；部分条目属于架构债务或条件性风险，不能统一称为可利用漏洞。

## 4. 第一轮发现

### AUD-01：执行合并不限制请求记录增长

**触发条件与机制：** 具有对应权限的用户反复使用新幂等键。余额刷新每次先插入 `room_operations`，已有刷新时再标记为 `merged`；30 秒冷却只在没有待办时检查。手动采集复用已有 run，但新键仍插入 `monitor_run_requests`。二维码刷新复用已有 operation，但新键仍插入 `payment_qr_requests`。学校执行去重不能限制这些持久映射的数量。

**影响：** 持续增加共享数据库的存储、索引和写入开销。余额结算还会一次读取全部合并记录，在同一事务中逐条更新，积压会延长事务。此项需要有效账号和对应业务前提，不是匿名越权；二维码路径还要求可用的对应订单。它是已修复历史受理问题之外的其他入口遗漏，不重开旧 `SEC-05`。

**建议与后续验证：** 在用户锁内统一检查新请求速率、待办和合并映射上限，保留同键重放；制定映射保留期。后续验证新键洪泛被预算阻止、同键重放仍可恢复、拒绝请求不留下半成品。当前未做真实请求洪泛实验。

**证据：** [余额受理 `accept_refresh`](../../backend/services/room/balance.py#L50)、[合并结算 `finish_operations`](../../backend/services/room/balance_store.py#L34)、[手动采集 `accept_run`](../../backend/services/monitoring/scheduler.py#L124)、[二维码映射 `refresh`](../../backend/services/payment/qr.py#L74)。

### AUD-02：已付款后的失败余额任务被无限回查

**触发条件与机制：** 支付已确认，关联的余额刷新 operation 进入 `failed` 或 `cancelled`。`balance_refresh()` 保存 operation ID 后只查原任务；读到任务失败时正常返回 `failed`，不会把 `error` 设为异常。领取条件却仍包含已付款且 `balance_refresh_state='failed'` 的订单，下一次回查按 `error` 为空安排在两秒后。

**影响：** 后台不断读取同一个已终结任务、更新订单版本，无法通过重复查询使其重新成功。用户另行手动刷新余额也不会自动替换旧关联 ID；这类订单累积后持续占用回查与数据库资源。该路径不是重复建单或重复付款。

**建议与后续验证：** 区分任务已失败和查询状态暂时失败；前者停止回查或进入有明确新操作及次数限制的重试流程，后者才退避。后续覆盖成功、任务失败、状态接口暂时失败和手动刷新后的订单表现。

**证据：** [领取条件](../../backend/services/payment/reconciliation.py#L15)、[原任务复用与状态映射](../../backend/services/payment/reconciliation.py#L41)、[下次回查时间](../../backend/services/payment/reconciliation.py#L114)。

### AUD-03：串行执行使慢任务阻塞后续任务

**触发条件与机制：** 支付回查循环等待一张订单全部处理完成，才领取下一张。每单两秒是其完成后设置的最早下次执行时间，不保证多个订单均以两秒周期被执行。Room 的绑定同步、余额刷新和历史窗口也在一个业务循环内依次执行。

**更正记录：** 第一轮中间分析曾认为支付每处理一单固定额外等待一秒；继续核对 `IdleBackoff.next(activity=True)` 后确认它返回 `0`，有任务时不额外等待。最终结论仅保留串行阻塞，不采用“50 单至少额外等待 50 秒”的错误推算。

**影响：** 多订单和慢学校请求会增加排队时间。例如假定每次处理一秒，50 个持续待查订单处理一轮约需 50 秒；这是指定假设下的模型估算，不是实际延迟。现有学校并发限制仍应保留。

**建议与后续验证：** 在学校限制内使用少量执行槽，保持账号串行和订单租约；观测到期至领取的等待时间。后续用受控慢任务验证其他账号公平性及原租约、副作用边界，不盲目扩大并发。

**证据：** [支付角色循环](../../backend/services/payment/process.py#L36)、[退避的活动分支](../../backend/services/common/scheduling.py#L37)、[单单处理](../../backend/services/payment/reconciliation.py#L147)、[Room 调度](../../backend/services/room/worker.py#L50)。

### AUD-04：快照清理吞吐不足，过期不代表预算立即释放

**触发条件与机制：** 每用户可保留 60,000 个成员，而一次清理全系统最多删除 1,000 个成员；recovery 约每 60 秒调用一次，即使仍有积压也不立即继续。配额按父快照的 `total` 统计，部分成员删掉后父行未删除，预算不会按已删成员逐步释放。

**影响与推算：** 单份 20,000 成员快照需要 20 批才能完全删除并释放该父快照的配额。50 个用户均接近成员上限时，300 万成员按每分钟 1,000 个需要约 50 小时才能清完，尚未计入新数据、故障或其他瓶颈。这是极限积压推算，不是普通使用必然发生的耗时。

**建议与后续验证：** 保留小事务，在时间及 I/O 预算内允许连续清理多批，记录积压量和最老过期时间。配额已防止原来的无限扩张，本项是恢复吞吐问题，不把旧 `SEC-03` 描述为完全未修复。后续验证满额用户恢复查询所需的批数及跨用户清理公平性。

**证据：** [配额统计](../../backend/services/monitoring/sample_snapshots.py#L60)、[清理上限及删除顺序](../../backend/services/monitoring/snapshot_cleanup.py#L6)、[固定触发周期](../../backend/services/monitoring/job.py#L158)。

### AUD-05：普通读取频繁写会话并争用控制行锁

**机制：** 已登录 API 请求的 introspection 通过 `SELECT ... FOR UPDATE` 读取会话及用户，再更新 `last_seen_at`、`expires_at`；`/auth/me` 还再次读取并更新会话。`/monitor` 通过 `lock_monitor()` 执行插入或重复键更新、取得监控行锁，再读取运行和通知信息。

**影响：** 轮询不只是读取，还产生事务提交及控制锁竞争。每域 `2+1` 小连接池下，会话更新与监控读取可能拖慢其他请求、控制和调度。未量化实际延迟；不能把所有锁直接删去，否则可能破坏一致性。

**建议与后续验证：** 保留实时会话有效性检查，降低续期写入频率；把监控首次初始化与日常读取分开，仅对需要一致性的字段保留必要事务。后续验证退出立即生效、绝对到期、读取与取消并发，比较实际写入次数。

**证据：** [会话读取续期](../../backend/services/identity/sessions.py#L25)、[重复会话检查](../../backend/services/identity/api.py#L118)、[监控读取](../../backend/services/monitoring/queries.py#L26)、[监控行锁](../../backend/services/monitoring/repository.py#L12)。

### AUD-06：分页中的历史关联判断缺少相应索引

**机制：** 每条样本的相关 `EXISTS` 查询查找相同 `meter_source_record_key` 的更早记录。当前索引为 `owner_user_id,binding_id,captured_at,id`，没有记录键字段。每次分页还对绑定全部样本执行 `COUNT(*)`，结果只用于判断是否存在历史。

**影响：** 历史增大时可能反复扫描较早记录，查找不存在的匹配尤其不利；分页返回上限不限制关联查询扫描量。实际执行计划、扫描行数和延迟未验证，不直接给出固定复杂度或性能提升比例。

**建议与后续验证：** 用代表性数据评估用户、绑定、记录键及时间的复合索引，将纯存在性判断改为存在性查询，同时计入新增索引的写入成本。

**证据：** [分页关联查询](../../backend/services/monitoring/samples.py#L83)、[历史计数](../../backend/services/monitoring/samples.py#L108)、[已有索引](../../backend/services/monitoring/migrations/versions/0001_initial.py#L238)。

### AUD-07：角色意外退出后的恢复缺口

**触发条件与机制：** 后台循环本身意外返回、抛出未被内部循环接住的异常或被取消。监督器只记录失败，不重建角色，也不让主进程退出。Compose 的 `restart: unless-stopped` 不会仅因 `unhealthy` 自动重启容器。

**影响：** API 主进程仍运行，但一个后台角色可长期停止，等待人工干预。常规依赖异常已有循环重试，本项不把这些异常都描述成角色退出。与 AUD-14 的区别是：本项任务已结束，AUD-14 的任务仍在运行但持续失败。

**建议与后续验证：** 明确角色安全重建，或协调停止后退出进程、由容器重启的策略。恢复继续依据租约和未知结果台账，不能重新发送未知支付或邮件。后续注入角色返回、异常及取消，验证恢复且无重复副作用。

**证据：** [角色退出处理](../../backend/services/common/background.py#L69)、[可用性判断](../../backend/services/common/background.py#L88)、[重启策略](../../deploy/compose.yaml#L7)。

### AUD-08：会话恢复强依赖 Adapter

**触发条件与机制：** `/auth/me` 在验证本地会话后同步调用 Adapter `/credentials/view`。Adapter 进程或其数据库不可用时，该请求失败，前端初始化进入 `unavailable`，受保护页面无法进入。

**影响：** 即使应用会话有效、Room 有已保存数据，局部 Adapter 故障仍阻断整个前端入口。这里指 Adapter 服务故障，不等同于学校网站故障；凭据展示本身不请求学校。

**建议与后续验证：** 分离必要应用身份恢复与学校凭据状态加载，学校能力故障时明确显示不可用，允许安全读取已有本地数据。后续验证 Adapter 停止时仍能恢复本地身份，同时不错误开放学校写入能力。

**证据：** [跨域会话信息](../../backend/services/identity/api.py#L25)、[前端初始化失败](../../frontend/src/features/auth/SessionProvider.jsx#L64)、[路由门禁](../../frontend/src/app/router.jsx#L5)。

### AUD-09：运行数据保留与归档尚未闭环

**机制：** 当前运行代码的明确物理删除主要是样本快照清理和学校历史窗口替换。已发布 Outbox、已处理 Inbox、过期应用会话、采集请求映射及运行和审计记录未形成完整定期归档清理链路。`monitor_run_requests` 写入七天到期时间，但未发现对应清理入口；Outbox 完成只是设置 `published_at`。

**影响：** 正常长期运行仍会扩大数据和索引，增加备份、恢复与查询成本。这里是生命周期欠账，不要求删除依法或业务上应保留的证据，也不把所有长期记录都视为缺陷。

**建议与后续验证：** 分别制定临时映射、传输去重记录和长期业务证据的保留／归档规则，遵守幂等和防重放窗口，明确外键顺序及未知状态保护。后续验证过期清理不导致旧消息重新生效、不丢失未解决台账。

**证据：** [映射到期字段](../../backend/services/monitoring/scheduler.py#L148)、[Outbox/Inbox 保存](../../backend/services/common/outbox.py#L72)、[审计写入](../../backend/services/audit/receiver.py#L8)。

## 5. 第二轮深入发现

### AUD-10：历史合并请求永久停留在 running

**触发条件与机制：** 一个跨多个七天窗口的同步存在合并请求，且合并发生在某个非最后窗口完成之前。合并时 `saga_step='merged'`；非最后窗口完成，`finish_sync()` 把主请求和合并请求都改为 `running / read_school`。后续传播 SQL 只包含主请求，以及 `upstream_operation_id` 匹配且仍为 `merged` 的请求，已经改名的合并请求不再命中。

**内存结果：** 原函数复现得到主请求最终 `succeeded / complete`，合并请求仍为 `running / read_school`，详见 E-01。此为 SQL 状态条件缺陷，不依赖 MySQL 特有的并发调度。

**影响：** 前端原操作不能收到终态，历史受理的非终态配额持续占用。待办计数不按日期过滤；累积 8 个卡住请求可持续阻止新受理，第二天不会自动释放。现有配额验收中的直接 `UPDATE` 完成模拟不能覆盖这条真实传播路径，不据此否定该测试所验证的受理预算。

**建议与后续验证：** 使用稳定的合并关系选择关联请求，不用可变执行阶段决定关系是否存在。处理已卡住的关联数据。定向覆盖两窗口及以上、合并发生在不同阶段、主请求成功或失败、配额最终释放；不得把合并请求提前标为完成。

**证据：** [合并建立](../../backend/services/room/history_jobs.py#L30)、[终态传播条件](../../backend/services/room/history_store.py#L42)、[无日期过滤的待办计数](../../backend/services/room/history_admission.py#L54)、[测试中的完成模拟](../../backend/tests/integration/test_history_admission.py#L104)。

### AUD-11：登录连接池占满后等待自身资源

**触发条件与机制：** `LoginSaga.locked()` 使用池内连接取得 `GET_LOCK()`，整个登录结束才释放。其内部的 `read()`、状态写入、用户提交和会话签发仍从同一 engine 取其他连接。core/低资源组合每域池为 `2+1`；三个登录同时持有各自命名锁连接时，内层操作再申请连接便无法推进，只能等待某个请求超时释放资源。

**内存结果：** 用原 `locked()`、`read()` 与容量 3 的连接池模型，把三个请求调度到同时持锁位置，三个内层读取均超时，详见 E-02。该结果证明资源占用关系，不代表任意三个并发登录都必然失败；生产配置的池等待为 3 秒，模型缩短时间只是便于观察。

**影响：** 并发登录失败，还会影响同池的会话检查、恢复与健康查询。即使没有长事务，学校认证期间仍长时间持有数据库连接。这是小连接池预算与登录锁实现之间的组合缺陷。

**建议与后续验证：** 消除持有池内连接再等待同池连接的结构；可考虑持久租约或独立且有受理上限的锁连接资源。不能仅扩大池或延长等待。后续在隔离 MySQL 中验证并发登录、慢认证、恢复任务同时运行、退出和命名锁释放。

**证据：** [命名锁](../../backend/services/identity/application/login.py#L92)、[锁内登录流程](../../backend/services/identity/application/login.py#L203)、[core 池配置](../../deploy/compose.core.yaml#L14)、[池等待上限](../../backend/services/common/database.py#L65)。

### AUD-12：OCR 超时后的底层线程并发

**触发条件与机制：** `asyncio.timeout` 取消等待 `asyncio.to_thread(solver, ...)` 的协程后，`ocr_lock` 被释放，但运行中的 Python 线程不会被强制终止。第二个请求可以取得异步锁并启动另一线程。

**内存结果：** 原认证函数与缓慢替代 solver 的两个调用均 deadline 到期，实际最大 solver 并行线程数为 2，详见 E-03。没有加载真实模型。

**影响：** 现有 OCR 串行约束在取消边界失效。冷启动时多个线程还可能同时进入 `lru_cache` 包装的首次模型计算；缓存一致不代表首次计算互斥。额外 CPU、内存峰值属于风险，本次未测真实峰值或证明发生 OOM。

**建议与后续验证：** 执行槽必须跟随真实计算完成才释放，限制等待队列并丢弃过期任务；如需要强制中止计算，应评估可终止的独立执行机制及资源成本。后续验证超时、排队、取消和冷启动时真实计算并发始终受限。

**证据：** [异步锁与线程等待](../../backend/services/school_adapter/application/background_auth.py#L11)、[模型缓存初始化](../../backend/services/school_adapter/infrastructure/ocr.py#L25)。

### AUD-13：余额写入缺少统一的新旧顺序

**触发条件与机制：** 监控 `/controls/balance-observed` 根据传入 `fetched_at` 条件更新；手动余额刷新、绑定同步则直接覆盖，并把时间设置为当前提交时间。旧请求取得结果后延迟返回或落库，新请求可能先保存新余额，旧请求随后覆盖新值并标为 `fresh`。旧失败还可能把后来成功的缓存标为 stale。

**影响：** 页面出现余额回退及错误的新鲜度。账号锁只覆盖学校访问，不能保证不同流程持久提交顺序。代码中的保护不一致已确认，实际并发重排尚未在数据库复现；不是余额凭空增加或学校账目被修改的证据。

**建议与后续验证：** 所有入口使用同一可信观测时间或单调版本，区分采集时间、返回时间与入库时间；旧成功和旧失败都不能覆盖较新结果。后续故意颠倒两次成功提交，以及旧失败和新成功的提交顺序。

**证据：** [有条件的监控写入](../../backend/services/room/query_api.py#L106)、[余额刷新直接覆盖](../../backend/services/room/balance_store.py#L20)、[绑定同步覆盖](../../backend/services/room/mirror.py#L47)。

### AUD-14：持续业务失败仍通过合并模式健康检查

**触发条件与机制：** 后台循环持续捕获业务异常，同时基础数据库／迁移检查等仍成功。`heartbeat.write(healthy=False)` 设为 degraded 并刷新 `last_tick`；`snapshot()` 依据最后一次 tick 判断是否失活。监督器接受 degraded，core 对 degraded 返回 HTTP 200，API 探针只看 HTTP 状态。

**影响：** 后台长期没有成功推进，容器仍可能显示健康。独立 Worker 的探针却要求 ready 和最近成功时间，部署组合间的健康语义不一致。临时 MQ 不可用而持久扫描仍能成功的降级是应保留的正常行为，不能一概把 degraded 改为失败。

**建议与后续验证：** 分开记录循环存活、业务成功扫描和依赖降级，给持续业务失败设置次数或时间预算。后续验证 MQ 故障但 SQL 扫描成功仍可降级运行，以及业务持续失败最终不能继续通过健康检查。AUD-07 处理的是角色已经退出，不能代替本项。

**证据：** [失败心跳与失活判断](../../backend/services/common/heartbeat.py#L28)、[监督器接受 degraded](../../backend/services/common/background.py#L88)、[core 状态码](../../backend/services/core/app.py#L47)、[独立 Worker 判定](../../backend/services/common/heartbeat.py#L57)。

### AUD-15：历史租约与完整执行预算不一致

**触发条件与机制：** 历史窗口领取租约为 45 秒，学校读取预算为 40 秒，但 Adapter 先回查 Room 目标，再开始学校读取预算；内部 HTTP 客户端的读取超时为 100 秒。Room 回写还需等待连接与偏好锁，而 `query_tick()` 没有为历史窗口续租。外层后台存活检查不等于续租。

**影响：** 在网络延迟、连接池拥塞或锁等待条件下，成功学校结果也可能因原租约过期被 `finish_history()` 丢弃。多次发生会消耗三次领取机会并以超时失败结束。该项是预算不一致的静态确认，不声称正常 40 秒内请求一定失败；HTTPX 的 100 秒是读取阶段配置，也不能当作完整链路的严格总时限。

**建议与后续验证：** 统一端到端 deadline 或使用受控续租，续租失败后停止接受迟到结果。后续分别延迟目标回查、学校读取和提交，验证结果落库、失租拒绝及尝试次数语义。

**证据：** [租约和尝试上限](../../backend/services/room/history_jobs.py#L128)、[学校预算前的目标回查](../../backend/services/school_adapter/query_api.py#L43)、[历史执行流程](../../backend/services/room/query_worker.py#L32)、[租约过期拒绝](../../backend/services/room/history_store.py#L63)、[HTTP 客户端超时](../../backend/services/common/service_client.py#L37)。

### AUD-16：core 直接分派缺少领域错误诊断

**机制：** Dispatcher 直接调用领域 endpoint，保留身份依赖及 DTO 校验，但不执行原领域 HTTP 中间件。未预料的异常被统一转换为 `ApiError(503, DEPENDENCY_UNAVAILABLE, ...)`，未记录领域、路由或原异常类型。外层接到的已经是 ApiError，通常只留下 Gateway 的请求完成记录，不进入原领域异常日志路径。

**影响：** 独立服务中能定位的 SQL／程序异常，在 core 模式可能只剩笼统 503，增加连接池和后台失败的定位成本。这是可诊断性差异，不是已确认的权限绕过。

**建议与后续验证：** 在分派边界记录脱敏的领域、操作、耗时、异常类别及请求 ID，保持对外错误简洁，不记录 SQL 参数、密钥或请求正文。后续用合成领域异常对比独立与 core 模式的可关联诊断。

**证据：** [分派及异常转换](../../backend/services/core/dispatch.py#L42)、[原领域 HTTP 日志](../../backend/services/common/http.py#L72)。

## 6. 三项纯内存复现记录

以下结果来自第二轮深入审计的实际工具输出；文档整理阶段没有重新运行。复现脚本当时通过 UTF-8 标准输入交给项目 Python，并使用 `-B` 禁止字节码写入。未保存为仓库测试文件，未调用应用启动入口。结果仅包含合成数据。

### E-01：历史多窗口终态传播（AUD-10）

- 从基线 `history_store.py` 的 AST 提取原 `finish_sync()`。
- 使用 SQLite `:memory:` 表，注册 `IF` 和 `UTC_TIMESTAMP` 所需的内存兼容函数，执行原函数中的 SQL；不模拟 MySQL 行锁或事务调度。
- 构造两个窗口、一个主请求和一个合并请求。第一窗口成功而第二窗口 pending 时调用一次；把第二窗口设为成功后再次调用。

```json
{"after_first_window":[{"id":"alias","state":"running","saga_step":"read_school"},{"id":"root","state":"running","saga_step":"read_school"}]}
{"after_final_window":[{"id":"alias","state":"running","saga_step":"read_school"},{"id":"root","state":"succeeded","saga_step":"complete"}]}
{"stuck_pending_aliases":1}
```

### E-02：登录连接嵌套申请（AUD-11）

- 提取原 `LoginSaga.__init__()`、`locked()` 和 `read()`。
- 使用容量为 3 的 semaphore 连接池模型；命名锁查询只返回合成的成功结果，不连接 MySQL。
- 使用同步点让三个请求都持有外层连接后再开始内层读取；将模型池等待缩短为 0.1 秒，不代表生产超时配置。

```json
{"pool_capacity":3,"held_before_nested_read":[3,3,3],"concurrent_login_results":["pool_timeout","pool_timeout","pool_timeout"],"remaining_connections_held":0}
```

该同步点选择了明确的风险调度场景，不能推导任意三个并发请求都必然失败。真实 MySQL 并发、取消后的命名锁释放和隔离模式仍待后续验证。

### E-03：OCR deadline 后的线程重叠（AUD-12）

- 提取原 `background_auth.authenticate()`，保留其超时、锁和 `to_thread` 控制流。
- 使用合成 challenge、0.03 秒预算和执行 0.18 秒的替代 solver；在线程安全计数器中记录活跃 solver 数。
- 顺序发起两个都超时的调用，等待遗留线程结束。未导入或初始化真实 OCR 模型。

```json
{"calls":["deadline_expired","deadline_expired"],"maximum_concurrent_solver_threads":2,"real_ocr_model_loaded":false,"network_used":false}
```

结果验证超时后的串行边界缺口；不验证真实识别速度、模型并发初始化次数、内存峰值或 OOM。
