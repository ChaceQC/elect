### R1.2 AUD-11：登录持锁执行槽与连接预留

**首选方案：** 保留现有跨进程 `GET_LOCK` 语义，先增加Identity进程内有界持锁执行门，避免多个外层命名锁占满同一业务池；暂不引入复杂的跨库登录租约，也不另开无上限连接池。

**初始参数：** 每个Identity上下文最多1个持命名锁的登录／恢复执行；最多2个短时等待者，等待上限250毫秒，超过后返回原429及重试提示。业务池仍为2+1，至少2个槽不被外层命名锁永久占住。该门限制的是本进程资源，不修改SEC-02/04对应的学校、浏览器或账号额度。

**实施步骤：**

1. 在同一个LoginSaga／Identity上下文中创建执行门，所有 `locked()` 路径，包括后台recover，都必须经过它；获取门之后才从engine拿命名锁连接，释放连接及命名锁后才归还门。
2. 禁止为每个请求各建一个门；取消、失败、超时、未拿到GET_LOCK等所有分支都必须归还已取得资源。命名锁释放失败应使相应连接失效，不能把可能持锁的连接正常放回池。
3. 已获执行门的流程可用现有内层事务推进；保留学校调用在SQL事务之外。应用会话读取不经过登录门。

### R3.3 AUD-07：不可恢复角色失败触发协调退出

1. Fatal通知有单一入口，区分SIGTERM正常关闭；只触发一次。core停止所有领域领取新任务，combined停止本域领取，独立worker退出自身。
2. 先停止新领取，再在已有各域退出预算内等待任务，预算耗尽才取消。保留心跳/租约/unknown台账，不人工把租约都清空为可重发。
3. ManagedServer需要收到fatal并结束运行，不能只返回健康503。非零退出码和失败原因可追踪；无外部autoheal脚本或额外守护容器。对OCR原生线程挂起，普通Python退出可能仍等待线程结束；fatal处理需在既定总退出预算内设独立的最终非零退出保障，不能只等待executor.shutdown或Uvicorn退出，也不能假设Docker会自动杀死unhealthy容器。该保障只在不可恢复失败和drain预算耗尽时触发，正常退出完成后撤销。
4. 持续依赖失败按R3.2预算触发，不因一次MQ短暂中断重启；重复故障有可观察记录，防止重启掩盖根因。
5. 恢复模式后台关闭时不得创建监督执行者，不因fatal机制把被禁止的后台启动起来。

2. 新增必要的owner/type/created_at与pending索引；手动映射、二维码映射若缺少可用创建时间，增量加列并对旧记录使用保守迁移时刻，不能凭空推断旧受理日期来提前删除。
3. 支付确认后的系统余额刷新使用受验证的内部调用方身份及原订单固定键，不能被浏览器伪造字段绕过预算；独立设置有界系统待办，确保被浏览器额度耗尽不会无限堆积。系统来源判定必须来自服务身份/登记用途，而非幂等键字符串前缀。

### R4.2 AUD-04：有积压时按预算连续清理

1. 保留单事务最多1000成员、最多4父快照的边界；有积压时每轮最多10批，软时间预算500毫秒，每批提交并归还连接后让出执行权。预算只决定是否开始下一批，不承诺正在执行的SQL必然在500毫秒内结束。
2. 有积压轮次建议1秒后继续，空闲时60秒；连接竞争或业务压力时降低清理频率。角色必须服从后台关闭和统一stop，不让回收吞掉业务池。
3. 选择过期快照时保留 `FOR UPDATE SKIP LOCKED`，评估按owner轮转或有界公平选择，避免大快照长期阻塞其他用户；新增索引需由真实执行计划支持。
4. 首轮仍按父快照total计配额，不引入容易漂移的第二套成员计数。通过连续小批把父快照清完后释放；如将来采用剩余成员计数，必须单独迁移并验证与删除同事务，不能只改SUM逻辑。
5. 记录待清成员、最老到期时间、每批删除数/耗时、跳过锁数量和因压力暂停次数。统计查询本身有界，不每秒全表COUNT。

**验收：** 20000成员的单快照、多个用户积压、到期时仍有分页共享锁、清理进程中断重跑、旧token404/410语义、原始样本不被删除。用一个可控积压数据集比较原实现与新实现，不反复扩容跑多套压力测试；输出每秒实际清理量和配额释放延迟，不预先声称300万成员已实测。

## 9. R5：在边界稳定后优化读取与调度

### R5.1 AUD-05：会话续期合并与监控无写读取

1. 会话每次请求仍读取权威撤销、用户状态、session_version、滑动及绝对到期时间；不以进程缓存替代撤销检查。
2. 将续期写入节流为每个会话最多每60秒一次，采用数据库条件更新，必须同时要求未撤销、版本有效、当前仍未过期；不能在读取后无条件延长已被撤销的会话。
3. 保留12小时滑动和7天绝对上限，明确最多60秒的续期粒度差异；若验收要求精确到每次请求的12小时，则采用等价的更细粒度合并方案，不悄悄改变有效期。到期前最后一段窗口要保证合法活动可续期，已过期绝不复活。
4. `/auth/me`和新R6本地会话入口每次至多做一次必要的身份检查，不把未经校验的浏览器字段当作已验证上下文传递。
5. `/monitor`只有首次不存在记录时走短事务初始化。正常读取采用独立的一致性读事务或等价单查询，避免一边读取旧配置一边拼接新运行状态；不改变全局READ COMMITTED配置。读取快照不用监控控制行的排他锁。

**验收：** 单会话连续读取时续期UPDATE次数符合上限；并行logout/禁用/版本更新后下一请求失效；滑动/绝对到期正确；首次并发初始化只有一条记录；monitor读取与取消/配置修改之间响应自洽。记录改动前后写次数、锁等待，不只记录HTTP200。

**文件：** Identity sessions/API、Gateway鉴权上下文、Monitoring queries/repository、会话与监控规则测试。无必要不增迁移。

### R5.3 AUD-03：有限槽位和按账号公平领取

**初始方案：** Payment回查两个执行槽；Room读取调度两个槽，在绑定同步、余额和历史之间做有界公平选择，控制Saga保持其独立角色。建单/表单写和邮件发送不因本项增加并发。各域仍用原2+1池，HTTP池和学校5/4/1预算不提高。

1. 领取时先选择可工作的owner并在本域owner锁内复核，再领取任务；同owner不允许多个同类学校读取同时执行。不能只依赖Adapter账号锁排队，否则会占住全部业务槽。
2. 使用已有owner行和任务租约表达在途状态，统一锁顺序，不能与取消/QR刷新形成反向锁。领取候选有上限且能跳过忙owner；不能反复只选到队首忙账号然后返回空。
3. 每槽持有独立任务身份/续租/取消控制，不共享单个可覆盖的lease变量。队列只保存少量已领取任务，不提前领取大量任务等待线程空闲。
4. 有工作时继续处理，空闲才退避；不恢复之前已更正的“每单固定sleep一秒”假设。慢任务用自身deadline结束，停止信号禁止下一次领取。
5. 监测各操作到期至领取的等待、处理时间、同owner等待及池耗尽；后台续租和API读取应有可取得连接的余量。若实测两个槽影响续租，先减少槽，不提高池掩盖问题。

**验收：** 一个合成慢账号持续等待时另一个账号可执行；多用户不会因队首忙账号饥饿；同owner仍互斥；重启、取消、旧epoch迟到不能重复提交；支付、历史、余额各自恢复规则保持。仅在50个合成用户目标场景做一次必要混合对照，不把它称为真实学校50人验收。

**R5退出条件：** 对照数据说明优化了哪项开销；没有牺牲身份检查、固定分页、控制响应或既定资源上限。

4. 保留BroadcastChannel、跨账号缓存清理、旧响应丢弃、登录成功后的协议阅读记忆；profile返回迟到时必须校验当前user/epoch。
5. 新前端访问旧后端时，仅在新端点明确404时按一次性兼容路径使用旧/auth/me；不能在503时循环请求两个入口。新后端继续满足旧前端的旧Me契约。

| R3 | 心跳/日志内部字段和监督退出信号 | 各种模式共用判定；恢复禁后台入口不受影响 |
| R4.1 | 映射创建时间及owner/时间/状态索引 | 新键预算、旧键重放、旧记录保留至少180天 |
| R4.2 | 清理调度及必要索引 | 不修改有效快照成员，不删除原始样本 |
| R4.3 | 各域归档目录/元数据及冷去重标识，保留策略 | 归档纳入备份恢复，冷标识故障不能绕过去重 |
| R5 | 可能增加样本索引；读取与执行调度变化 | 不改金额精度、分页total、学校并发和业务池上限 |
| R6 | 新增本地会话API和生成契约 | 旧Me和登录响应兼容；前后端有明确升级顺序 |

所有新增迁移都同步schema catalog、迁移头清单、契约说明及恢复/部署脚本的必要检查。运行时不读取源码推断迁移头。表字段扩展优先nullable或安全默认，只有完成回填后才考虑收紧约束。

### 11.1 存量命令的共同要求

- dry-run为默认，只选择指定领域、状态和范围；输出候选、可修、跳过、冲突计数。apply需显式模式和目标，不能隐藏在普通服务启动中。
- 每批事务有上限，使用实际归属和当前状态重新确认；有断点、幂等和停止能力。重跑不能再次改变已正确处理的结果。
- 先生成受控审查摘要及必要备份；原始数据不得作为公开JSON或文档提交。正常业务未知结果和发送标记不得被批量改成功、删除或重新派发。
- 数据处理脚本不做跨领域直连运行时查询；需要跨域校验的维护操作使用独立受控运维权限，不能把该权限交给普通服务。
- 删除与正确性修复不可等同回滚：修正后的终态、观测顺序和防重放标记一般保持，镜像回退必须检查旧代码能否安全理解扩展数据。

### 11.2 各类回退的实际限制

| 变化 | 可采用的回退方式 | 禁止的简化处理 |
| --- | --- | --- |
| 历史终态与支付后失败调度修复 | 保留正确终态及停止的无效调度，回退至含最小修复的已验证代码 | 为“还原”而把成功别名改回running、把失败订单重新加入无限回查 |
| 登录/OCR有界执行 | 保留安全执行门；紧急时降低受理或暂停自动OCR，人工登录保留 | 恢复无界等待、忽略运行中的识别线程 |
| 余额序号与新增内部DTO | 停全部新旧写入者，协调回退生产者/消费者；保留扩展列并检查计数高水位 | 只回退Room或Adapter一边、重新从零计数、清掉新鲜度字段 |
| 健康/协调退出 | 诊断、状态判定与退出联动作为完整单元回退，保留人工可定位的失败信号 | 让探针绿色掩盖后台停止或持续错误 |
| 新受理预算与清理速度 | 保留字段和索引，按已验证参数降载；清理可暂停，已有幂等记录保留 | 删除超过新配额的旧记录、放宽总量上限掩盖清理停滞 |
| 冷归档/去重 | 旧代码若不识别冷标识，先在停消费窗口将所需标识回填热表并验证去重，或只回退到支持冷标识的版本 | 直接切回只查热Inbox/映射的旧镜像，导致旧消息或请求重新执行 |
| 查询索引与有限槽 | 保留兼容索引，执行槽可降为1；保留新租约/停止边界 | 在在途任务未结束时切换领取协议，破坏执行唯一性 |
| 新本地会话API | 保留旧/auth/me契约，优先回退前端，后端增量入口可暂留 | 新前端依赖未部署的接口、通过伪造学号或权限状态维持页面 |

恢复已删除的有效期外数据只能使用经过验证的归档/备份流程；不能为恢复查询而同时激活旧支付、邮件、Outbox或会话。以上回退步骤只在获得相应目标环境操作授权后执行。
